# git 历史口令清理评估报告（T-A4 / AC3，报主控转产品负责人裁决）

> 结论先行：**建议不重写历史**，以「轮换本机开发口令使旧值失效」兜底；若坚持清历史，按 L3 单独开卡低峰执行。未裁决前只清 HEAD 不动历史（本卡已完成 HEAD 清理，本报告不动任何历史提交）。

## 1 事实

- 泄漏值 `family-menu-local-2026`（撰写本报告时已在 HEAD 全部清除）经 T-A4 立项前核查＝**本机开发口令**，与生产 ACCESS_TOKEN 不同且生产已轮换——不是有效生产凭据。
- 该值随 tests/tools/evidence 等文件于 2026-09-04（TP-01 时期）前后的多个提交进入历史，此后每个后代提交的树对象都含它；git 历史中**不可通过删除文件清除**。

## 2 重写影响面（filter-repo 与 BFG 相同）

1. 所有触及提交及其全部后代提交的哈希改变——本项目提交历史连续密集，**近乎全部提交哈希失效**。
2. 证据引用链断裂：evidence/、开发日志.md、OPS-LOG.md、CURRENT.md、任务卡中记录的全部提交号失去指向；「版本号＝提交号」的生产对应关系破坏（生产 API 容器 `9caa1d8` 将无法在仓库中找到）。
3. 远端需强制推送；所有克隆（本机、服务器、可能的备份）必须重新克隆或 `--rebase` 校准，漏一处则旧历史经 push 复活。
4. 生产容器镜像由旧提交构建，镜像层仍含旧值；清历史不清镜像。

## 3 三列对比

| 方案 | 成本 | 风险 | 收益 |
|---|---|---|---|
| ① 轮换本机开发口令＋不重写 | 改本机 .env 一处＋重启本地 API，约 10 分钟 | 几乎为零；历史明文永久可见，但该值已失效且非生产凭据 | 保住全部提交哈希与证据引用链；满足「口令不再有效」的安全实质 |
| ② git filter-repo 重写 | 执行＋全端重新克隆/推送＋证据链逐条修复，估半天起步 | 高：哈希断裂不可逆；生产镜像与提交失配；误操作丢历史；漏克隆致旧值复活 | 历史中不再可见该明文（仅此一项） |
| ③ BFG 重写 | 同②（另需安装 Java/BFG，本机环境未备） | 同②，且对本项目「值散布在多类文件」场景需自定义规则，误删面更大 | 同② |

## 4 建议

- **首选①**：轮换本机开发口令（需产品负责人/主控在本机 .env 操作，开发智能体禁碰 .env），旧值即成为无害死字符串；配合本卡新增的 `pnpm check:secrets` 防复发。
- 若产品负责人仍要清历史：按 L3 走（备份 bundle → 低峰窗口 → filter-repo → force push → 全端重新克隆 → 证据链修复单独开卡），并接受生产镜像与提交号失配。
- 明确边界：**未裁决前不动历史**；本卡交付只覆盖 HEAD。
