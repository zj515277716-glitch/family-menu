## 二、putExclusions 全量替换语义风险评估专节（review S-4）

### 2.1 源码级事实

- `apps/api/src/services/planService.ts` L352-370：`putExclusions` 在事务内先 `deleteMany({ where: { familyId: FAMILY_ID } })` 再 `createMany(payload 全量)` —— **全量替换语义**，familyId 强制覆盖为 `seed-family`
- 入口：`apps/api/src/routes/family.ts` L48-56 `PUT /api/family/exclusions`（PutExclusionsRequestSchema = z.array(ExclusionRuleSchema)，无 superRefine 交叉校验）
- 前端：`apps/h5/src/api/client.ts` L79-81 `putExclusions(rules)`；`apps/h5/src/pages/setup/index.tsx`：
  - L53-73 `loadRule`：GET exclusions 写入本地 state；**GET 失败仅 console.error，state 保持 []**
  - L75-108 `handleSave`：每次点「保存设置」都执行 `api.putExclusions(exclusions)` —— **本地 state 全量回传**

### 2.2 风险结论（已用回滚事务实证）

1. **一次 PUT 即清除 seed 规则**：只要 PUT payload 不含 seed 三条规则（如 UI 本地 state 为空/加载失败后保存，或用户提交自建规则集），deleteMany 会把 seed-excl-peanut-ing（HARD 花生食材级）连同 seed-excl-peanut、seed-excl-organ 一起删除——本卡修复的拦截力随之归零。v3 中间态实证：PUT 后仅剩 payload 1 条，INGREDIENT 行=0。
2. **静默全清场景**：loadRule 网络失败后用户仍可点保存 → PUT([]) → deleteMany 删光 + createMany 空 = 全表清空，无任何提示。
3. **UI 自建规则有效性缺口**（同族问题）：setup 页 addExclusion（L129-137）把用户输入文本直接写入 targetId（INGREDIENT/DISH scope），INGREDIENT 通道仅当该文本精确等于食材名/别名才拦截（输入「花生」拦不住「花生米」），DISH 通道文本永远匹配不到 dish.id——UI 自建规则大多形同虚设。
4. **回读可读性缺口**：GET /api/family/exclusions 返回纯 ExclusionRule 行（getExclusions 不经 toExclusionView），无 targetName/targetAliases，H5 exTargetLabel 对 seed-excl-peanut-ing 显示为一串 cuid 而非「花生米」。

### 2.3 处置建议候选（本卡未改代码，转主控挂账裁决）

| # | 候选 | 要点 | 利 | 弊 |
|---|---|---|---|---|
| 1 | **API 层 seed 保护** | putExclusions 删除阶段排除 `id LIKE 'seed-%'`（或在 createMany 后 upsert 补回 seed 规则） | 不动契约、不动前端，侵入最小，立刻堵住「意外清除」 | 「seed-」前缀成为魔法约定需文档化；用户仍可通过 PUT 提交同名 id 覆盖 seed 规则内容 |
| 2 | **写语义改造** | PUT 改为增量 upsert + 显式删除列表（契约增 deletions 字段），或保留 payload 外未知 id | 语义最干净，根治全量替换隐患 | 需 packages/shared 契约变更 + 前端配合，须架构师影响评估 + 用户批准 |
| 3 | **数据来源标记** | ExclusionRule 加 source 列（SEED/USER）+ 迁移；PUT 仅允许触碰 USER 行 | 保护最彻底，seed 规则与用户规则职责清晰 | 契约 + DB 迁移双变更，成本最高；建议作为长期正解 |
| 4 | **前端兜底** | H5 handleSave 前重新 GET exclusions 与本地 state 合并；loadRule 失败时禁用保存并提示 | 纯 H5 改动，阻止「空 state 全清」的意外路径 | 不解决用户主动删除 seed 规则的口子；两端行为仍依赖约定 |
| 5 | **文档口径（短期运维兜底）** | 明确「PUT 清除后 `pnpm db:seed` 重放即可恢复 seed 规则」（upsert 幂等已验证） | 零代码成本，可与任一方案叠加 | 属事后恢复而非预防；个人自用版可接受的临时口径 |

**DEV 推荐组合**：短期 = 候选 1 + 候选 4 + 候选 5；长期挂账 = 候选 3。最终裁决权在主控/用户。
