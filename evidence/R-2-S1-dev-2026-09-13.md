## 六、遇到的问题与处置

1. **pnpm `--` 字面透传（卡外备案，移交主控）**：任务卡 AC1 引用的 `run publish-check -- --help` 形态在本机 pnpm（Windows/PowerShell）将 `--` 与 `--help` 字面透传给脚本（实际执行 `tsx src/cli/publish-check.ts "--" "--help"`），commander 报 `error: too many arguments. Expected 0 arguments but got 1: --help.` EXIT=1；import 侧则把 `--help` 当 <file> 实参报「文件不存在：--help」EXIT=1。**重构前后均同错**（见 §三 #4/#5），证明与本次改动无关、属既有环境行为。AC1 意图（正式口径行为不变）以等价无 `--` 形态验证（EXIT=0）+ 字面形态前后逐字同错对照双路证实。未擅自改任务卡、package.json 脚本或 pnpm 配置，移交主控裁决（如后续修脚本可用 `pnpm --filter … run publish-check --help` 直传或改用 npm run 语义）。
2. **isMain 守卫在 vitest 进程内恒 false → 守卫 catch 块不可达**：守卫块是模块内非导出代码，单测 import 时 isMain=false 不执行，故「publish-check 执行失败：」「import 执行失败：」文案 + exit(1) 无法在测试进程内自然触达。处置：PC-a / IMP-c 两用例先用真实 action 抛错驱动 parseAsync reject 断言 rejection 形态，再**在测试内逐字复现守卫 catch 回调**（与源码逐字一致，注释注明）驱动真实 rejection 锚定 stderr 文案与 exit(1) 截获；守卫块真实口径另以 tsx 实跑双锚定（§三 #6/#7，EXIT=1 + 同文案）。未验证项：vitest 进程内对守卫块本体的执行覆盖（技术不可达，非本卡遗漏）。
3. **process.exit mock 后 action 继续执行（trailing rejection，如实记录）**：exit spy mockImplementation 返回 undefined 后，exit(1) 路径的 action 不会终止：IMP-a 继续执行 readFileSync → 抛 ENOENT → parseAsync reject；IMP-b 若文件内容合法会继续跑库链路。处置：IMP-a 对 trailing ENOENT rejection 按实际行为断言（`rejected` instanceof Error 且 code=ENOENT）；IMP-b 故意配非法 JSON 文件使 prepareDraftDish 内 JSON.parse 立即抛 SyntaxError 终止（createPrismaDraftWriter 未调用断言在案，库链路零触达）。两处均已在用例注释与本报告注明：trailing rejection 系 exit mock 的测试形态，非产品缺陷（真实口径下 process.exit 不返回）。
4. **commander 15 同一 program 实例重复 parseAsync 的状态残留确认**：核对 commander 15.0.0 源码——构造器默认 `_storeOptionsAsProperties = false`（command.js L41），且 `_prepareForParse()` 首次 parse 保存状态、后续每次 parse 前恢复快照（saveStateBeforeParse/restoreStateBeforeParse，L1118-L1187）。结论：同一 program 实例重复 parseAsync 安全，PC-d 的 `--json` flag 不会泄漏到 PC-e（已按此设计用例，12/12 通过佐证）。
5. **commander parse 阶段错误不走守卫 catch**：实测缺参输出 `error: missing required argument 'file'` 无「import 执行失败：」前缀，确认 commander 对 parse 阶段错误直接 process.exit(1)（不 reject、不经守卫 catch）；仅 action 内 throw 才 reject 进守卫 catch。该事实决定 PC-a/IMP-c 用 action 内错误驱动（见 §六-2），并作为用例设计依据记录于 spec 文件头。
