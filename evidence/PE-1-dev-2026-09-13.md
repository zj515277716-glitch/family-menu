### 改了什么（4 处，均在 index.tsx）

1. **removedIds 状态**（[index.tsx L41-44](file:///d:/codex/family-menu/apps/h5/src/pages/setup/index.tsx#L41-L44)）：新增 `useState<Set<string>>(new Set())`，承载本次编辑会话内的删除记录；注释载明产品口径（用户行=用户数据删除须持久化；seed 行=出厂配置，删除后保存仍由 API 层 seed 保护复活）。
2. **removeExclusion**（[index.tsx L182-187](file:///d:/codex/family-menu/apps/h5/src/pages/setup/index.tsx#L182-L187)）：删除本地行的同时以函数式更新记录待删 id（`setRemovedIds(prev => new Set(prev).add(id))`，防闭包旧值）。
3. **handleSave 合并与清空时机**（[index.tsx L115-133](file:///d:/codex/family-menu/apps/h5/src/pages/setup/index.tsx#L115-L133)）：远端追加过滤改为 `remote.filter((r) => !localIds.has(r.id) && !removedIds.has(r.id))`；`api.putExclusions(merged)` 成功后才 `setRemovedIds(new Set())` 清空——re-GET 抛错中止或 PUT 失败走 catch 时 removedIds 保留，用户重试保存仍生效。注释完整披露两侧语义：用户行删除→不进 payload→deleteMany 清除→持久化；seed 行删除→同样不进 payload→库内 seed 行受 API 层保护仍在→保存后/重进页面复活（S-5 语义保持，长期方案 3 另立卡）。
4. **S2 搭车**（[index.tsx L47-50](file:///d:/codex/family-menu/apps/h5/src/pages/setup/index.tsx#L47-L50)）：`exclusionsLoadFailed` 初始值 `false`→`true`（加载中视为不可保存）。settle 后由 loadRule 的 allSettled 分路置位（[L82-91](file:///d:/codex/family-menu/apps/h5/src/pages/setup/index.tsx#L82-L91)：fulfilled→false / rejected→true），Promise.allSettled 每结果仅两态，分支穷尽无遗漏。

### 为什么

- **T-1**：改动前 handleSave 直接 `PUT(本地 state)`，用户行删除可持久化；改动后 `[...exclusions, ...remote.filter(r => !localIds.has(r.id))]` 会把远端仍存在的已删用户行追加回 payload，用户删除被保存动作静默回滚——相对改动前的真实行为回归。按主控裁决采用 removedIds 集合最小修复。
- **S2**：初始 false 使 loadRule settle 前保存按钮可用，存在「空 state 保存」窗口；初始 true 在既有双层兜底（re-GET 合并 + API 层 seed 保护）之上补齐时序防护。

### 披露补齐核对（planService.ts / routes/family.ts 未动的理由）

- planService.ts putExclusions 注释块与 routes/family.ts PUT 路由注释中的 S-5 表述「UI 删除的 seed 规则保存后会被复活」在新实现下**仍为真**：seed 行删除经 removedIds 排除出 payload → API 层 deleteMany 永不删 seed 行 / createMany 不过滤写入 seed 行 → 库内行仍在 → 下次 GET/重进页面复活。按任务书「若一致保持不动」指示，两文件零改动。用户行删除持久化的披露落在 index.tsx 三处注释（state 声明 / removeExclusion / handleSave 合并处）。
