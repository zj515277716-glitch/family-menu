## 5. 卡外发现与流程记录（按铁律 2 报告，不顺手修改）

1. **fm-arch 越界修改**：架构师在 DEC-012 影响评估时，除评估结论外直接修改了 `packages/shared/src/schemas/api.ts`（其权限范围内，AGENTS.md 允许）与 `apps/h5/src/types/index.ts`（**越界**，属 WP-05）。改动内容经核验正确（unmetMustUse 类型声明与契约一致），流程违规记录在案；后续切片派发时明确"评估与实施分离"。
2. **swapPlan 必消原文问题（移交 TP-03）**：[planService.ts](../apps/api/src/services/planService.ts) `swapPlan`「全换」路径将 `plan.context.mustUse`（**用户原文**）直接传入 `recommend({ context: { mustUseIngredients } })`，未经 TP-02 的原文→ID 归一映射。TP-02 落地后此路径会把中文原文当 ingredientId 匹配 → 新引擎判定匹配不到 → 整套换可能空手/行为异常。属换菜切片范围，不在本卡顺手修改。
3. **dist 陷阱（环境经验）**：`packages/engine` 与 `packages/shared` 的 package.json `main/exports` 均指向 `./dist/index.js`——vitest 直接跑 src（全绿）但 API（tsx watch）加载 dist 旧编译产物。**改 engine/shared 源码后必须 `pnpm --filter @family-menu/shared build` + `pnpm --filter @family-menu/engine build` 再跑 e2e**，否则 e2e 静默走旧逻辑（本次曾致空手用例 FAIL：candidates=2、unmetMustUse=undefined）。
4. **沙箱常驻进程（环境经验）**：node 脚本内 execFileSync 启动的常驻进程会随脚本退出被整树回收（0xC000013A）；PG 与 API dev 均须以 `Start-Process` 创建独立进程方式启动，才能在脚本结束后存活。
5. 性能基准与 dev 进程争 CPU 的排查结论见 2.3，非代码缺陷。
