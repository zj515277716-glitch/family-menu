## 背景

T-C07 证实安全过滤铁律级缺口后已落地 PE-1（API 层 putExclusions seed 保护）与 T-C07-FIX（seed 补 INGREDIENT 级 HARD 规则），engine 侧拦截链已闭环。但内容入口（tools/content-pipeline）仍无过敏原校验环节：含过敏原食材的菜可以无任何标注地入库为 DRAFT，未来人工发布确认时若无工具化检查，含花生菜将以 flavorTags 缺「花生」的形态进入 PUBLISHED 推荐池（依赖发布人记忆把关，无系统保障）。方案 C 可取形态要求：内容管线（WP-07）加校验「含过敏原食材的菜必须 flavorTags 含对应 tag 方可进入发布轨道」。

## 目标

给内容管线补两道过敏原纵深防线 + 一个 category 漂移警告面（R-1 防御），全部约束在 tools/content-pipeline 包内，不涉 packages/shared 修改、不碰 engine、不碰 DB schema。

## AC（逐条 [✓]/[✗] 自检，证据落盘 evidence/R-2-dev-2026-09-13.md）

- **AC1 fm-import 入库过敏原校验（HARD 拒绝 / SOFT 警告 / 显式豁免 flag）**：fm-import 在写库前对导入 JSON 的食材清单做过敏原暴露检测；规则源=DB ExclusionRule 全量（当前 4 行：seed-excl-peanut TAG HARD / seed-excl-organ TAG SOFT / ex-1788658316681 腊肉 INGREDIENT SOFT / seed-excl-peanut-ing 花生米 INGREDIENT HARD；规则集动态读取非硬编码）。匹配口径：INGREDIENT 规则按食材 id/name/aliases 精确等值（对齐 engine checkIngredientScope 口径，须经 DB 食材行 join 补全 aliases）；TAG 规则按食材 name/aliases 含 targetTag（子串宽口径，纵深补位 engine TAG 通道不查 name/aliases 的已知缺口——管线侧误伤代价低，由豁免 flag 承接人工裁量）。合规判定：待导入菜 flavorTags 含 targetTag 即视为已标注（engine 会拦，管线放行）。处置分级：命中 HARD 规则且未标注 → **默认拒绝导入（exit 非 0，输出命中明细）**，`--allow-allergen-draft` 显式豁免方放行（放行时打警告行）；命中 SOFT 规则且未标注 → 警告不阻断。无 ExclusionRule 行（空规则集）→ 校验空转零影响。测试须覆盖：HARD 拒绝/豁免放行/SOFT 警告/已标注放行/无命中放行 五分支。
- **AC2 fm-publish-check 发布前置只读盘点 CLI**：新增 CLI（package.json bin 注册 fm-publish-check），扫描 status IN ('DRAFT','TESTED') 全部菜（Dish→DishIngredient→Ingredient 联查），按 AC1 同口径检测过敏原 tag 缺口，输出人类可读+结构化报告（菜名/origin/status/命中规则 id/规则 severity/缺失 targetTag/命中的食材与 aliases 明细）；**严格只读零写库**。退出码约定：0=无缺口、2=存在缺口（对齐 batch-fetch exit 2 先例，便于未来接入自动化）、1=自身运行错误。支持 `--status draft,tested` 过滤参数（缺省全扫）。
- **AC3 category 漂移警告（R-1 防御面）**：fm-import 对食材 category 不在 shared CATEGORIES 六类（管线侧 import 消费常量，非修改 shared）的行打警告（含食材名与当前值、六类清单），不阻断不改变退出码；fm-publish-check 报告附非标 category 食材计数。R-1 书面认定已裁决库层容忍存量（嫩豆腐不动），本 AC 只管新增入口的可见性。
