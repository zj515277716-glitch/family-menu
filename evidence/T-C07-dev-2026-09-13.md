## 一、结论摘要（TL;DR）

1. **【已证实】花生过敏 HARD 规则对全库 49 道菜的拦截能力为零。** 运行时用真实库数据执行生产 dist 代码 `safetyFilter`（import 自 `packages/engine/dist/safety.js` 与 `apps/api/dist/services/mappers.js`）：全库 49 道单菜合成过滤，被拦 **0**、通过 **49**；含花生成分的 2 道菜（宫保鸡丁、蚝油生菜，均 DRAFT）**全部未被拦截**。
2. **【已证实】缺口机制**：HARD+TAG 匹配口径 = 菜品 `flavorTags` 数组**等值包含** 或 食材 `category` **等值**（[safety.ts checkTagScope L103-127](../../packages/engine/src/safety.ts#L103-L127)）。全库 0 道菜 flavorTags 含「花生」、0 个食材 category=「花生」（category 取值域无此品类），花生仅以**食材名/别名**形态存在（花生米/熟花生米/油炸花生米），而 TAG 通道**完全不读食材名与别名**——规则口径 × 数据形态交集为空。
3. **【已证实】引擎通道本身是活的，死的不是代码是口径**：同样真实数据下——追加 HARD+INGREDIENT(花生米) 内存规则即拦 2/2（含 `optional=true` 行）；给菜品 flavorTags 补「花生」即拦；把 targetTag 改「调料」拦 46/49。
4. **【已证实】当前 PUBLISHED 推荐池（18 菜 / 12 菜单）恰好不含花生——是数据巧合而非机制保障**。2 道含花生菜均为 DRAFT，一旦经内容管线转 PUBLISHED 即进入暴露状态；换菜链 `filterSwapCandidates` 复用同一 `safetyFilter`（[swap-candidates.ts L3/L51](../../packages/engine/src/swap-candidates.ts#L51)），同样不拦。
5. **【已证实】S-3 观察成立（非证伪）**：T-C06 review 的静态推断「可能不被拦截」升级为运行时实证「不被拦截」。测试基线全绿而缺口长期未暴露的原因：engine 既有 TAG 用例全部是「flavorTags 恰含目标串」的构造场景（水产/麻辣/内脏），无「食材名≠品类」的真实形态用例（见 §3.4）。
6. 同族扫描【已证实】：全库仅 2 条 ExclusionRule；SOFT+TAG 内脏为**完全死规则**（三口径全 0，当前无内脏族食材，无现实暴露对象）；无其它 HARD 规则、无 INGREDIENT/DISH scope 规则（2/2 全覆盖）。

## 六、AC4 处置方案（≥2 案，含影响面/风险/推荐序）

### 方案 A（推荐）：seed 层新增 HARD+INGREDIENT 规则，复用现成食材通道

- **改动位置与形态**：`apps/api/prisma/seed-data.ts` exclusionRules 数组新增一行 `{ scope:'INGREDIENT', targetId:'cmtvnuvxvc2oy5fdrzhpxxe69', severity:'HARD', note:'孩子花生过敏（食材级：花生米/熟花生米/油炸花生米）' }`；**保留**原 TAG 规则（若未来真有菜打「花生」风味 tag 仍拦，双保险）。生产库落地方式（seed 重放 / migration）由实现卡定。
- **生效机制（已实证）**：`loadExclusionViews` L107-109 对 INGREDIENT 行 join Ingredient → `toExclusionView` 带 targetName/targetAliases → `checkIngredientScope` 精确等值（id+name+aliases），C1 运行时实证拦 2/2、optional=true 行同拦。
- **影响面**：engine 零改动、shared 零改动、api 装配链零改动（通道现成）；影响仅数据/迁移面，回滚=删规则行，成本最低。
- **风险与副作用**：
  1. `checkUnconfirmedIngredients` 被激活（存在 HARD+INGREDIENT 规则后，ingredients 为空的菜被保守过滤）。**当前库影响面=0（已证实）**：0 食材行菜 = 0 道、含此类菜的 PUBLISHED 菜单 = 0 个（v5 实测）。未来内容管线产出无食材行菜时会被拦——方向为安全侧（保守过滤），为 engine 既有设计。
  2. 「新增食材即漏」固有弱点：未来录入「花生酱」等新花生族食材需各挂一行规则（或录入流程把关）。精确等值匹配**不误伤**（「花生油」不会被「花生米」规则拦——精炼花生油医学上多数花生过敏者可食，语义可辩护；若要拦再补一行）。
  3. seed.spec.ts 若断言规则数量需同步调整（属实现卡范畴）。
  4. RDS 另立卡（任务卡约束）。

### 方案 B（备选）：engine 层扩展 TAG 匹配到食材 name/aliases（contains 泛匹配）

- **改动位置与形态**：`packages/engine/src/safety.ts` `checkTagScope`（L117-124）在 `ing.category === tag` 之外增加「ingredientName 含 tag 或 aliases 含 tag」（子串匹配）。
- **影响面**：engine 单文件 + engine 测试；api 装配链零改动（DishIngredientView 本就携带 ingredientName/aliases）；shared 零改动。
- **风险与副作用**（核心）：
  1. **泛匹配误伤面**：规则语义从「标签」漂移为「子串」。反例推演（静态推断）：targetTag='蛋' 会把「皮蛋」与「鸡蛋」一并命中（可能合意），targetTag='油' 会拦一切含油食材的菜（必然误伤全库）；「花生」规则会拦含「花生油」食材的菜（保守方向误伤，压缩推荐池）。
  2. **过敏原语义本不是子串关系**：「花生」规则永远盖不住「腰果/杏仁/核桃」等其它坚果——泛化匹配给不了正确过敏原语义，坚果族仍需显式规则集。
  3. 三 scope（DISH/INGREDIENT/TAG）的产品语义边界被打破（TAG 兼任 INGREDIENT），规则模型解释成本上升。
- **若采纳**：必跑 `pnpm test:taboo`（铁律），并逐 targetTag 词表评估误伤面（实现卡）。

### 方案 C（不单独作为修复）：数据面给含花生菜补 flavorTags='花生'

- **改动位置与形态**：菜品 flavorTags 字段（seed/内容管线产物）。
- **生效机制（已实证）**：C2 显示 flavorTags=['家常','花生'] 即拦。
- **风险与副作用**：**最脆弱**——每道含花生新菜都须记得打标，内容管线无此校验环节，漏标即漏拦；且 flavorTags 是风味标签（家常/咸香/清淡…），塞过敏原属语义污染，前端展示同步露馅。
