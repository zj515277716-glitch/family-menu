# AI 协作开发流程 V2.1（精简可复用版）

> 适用：**非程序员产品负责人 + AI 编码智能体**开发中小型应用（新项目、存量改造、日常迭代），主要工具为 **TRAE CN**（也兼容 Claude Code / Codex）。
> 来源：两个项目的实践复盘——
> - 家庭菜谱（`family-menu/复盘报告_V2_2026-09-29.md`）：证据空转、流程倒挂、生产不可追溯；
> - 农产品信息交易平台（`OPC项目/买菜平台/复盘报告_2026-09-29.md`）：按 V1.0 四角色流程开发，证据真实，但 UI 不满意、缺整体设计，13 张卡里 9 张是真机测出的问题。
> 与 V1.0 的关系：
> - **保留**：三对齐（需求 / UI / 功能）、证据能证明什么、缺陷处理八步、四类打断用户的情形。
> - **删改**：固定四角色全流程、每卡多份证据、无边界的挂账执行。
> - **新增**：风险分级、系统不变量、发布流水线、文档预算、健康度指标；V2.1 再加**开发前设计包（第 3 章）、UI 与视觉（第 4 章）、页面自动化验收、TRAE CN 落地（第 9 章）**。
> 状态：建议稿。在某个项目采用时，**必须同时改写该项目的唯一规则入口**（第 9 章），否则不生效。

---

## 0. 十二条原则

1. **先走通一条真实旅程，再扩功能。** 第一周就要做到：真实数据库、真实部署、在真实手机上完成一次核心任务。
2. **先设计整体，再做单页。** 开发前要有导航图、角色视图、会话流程和平台约束调研；行为表按用户旅程写，不按功能写。
3. **视觉风格单独对齐，在目标设备上确认。** 用参考截图和成熟组件库，不让写代码的 AI 凭空画界面。
4. **AI 必须能看到自己做的页面。** 页面由自动化工具打开、点击、截图，AI 先自己验过，你只做体验确认。
5. **能交给机器的规则，不写成文档。** 优先用 CI、脚本、钩子和权限来约束；文档只写机器表达不了的东西。
6. **流程强度按风险分级（L0–L3）**，不按"当时在不在走流程"来决定。
7. **验收看用户结果和系统不变量。** AC 只是补充，不能代替。
8. **生产只认流水线。** 同一份产物、有版本号、可回滚；不手工改生产；验收环境与正式环境分开。
9. **本地要像生产。** 运行时版本、数据结构、构建方式都保持一致。
10. **同一现象修两次还没好，就停下来**，换一个干净的上下文做根因分析。
11. **用户只做产品决策。** 技术选择由 AI 决定并记录；安全、费用、生产数据、不可逆操作必须问，而且必须等到明确答复。
12. **状态一屏、入口唯一、挂账有上限，每个阶段结束做一次减法。** 流程自己产生的工作量不能超过产品本身。

## 1. 角色（是"职责"，不是"必须开几个会话"）

| 职责 | 由谁承担 | 要点 |
|---|---|---|
| 产品负责人 | 你 | 确认需求、导航、视觉和体验；授权费用、账号、上线和生产数据操作 |
| 主控 | TRAE 主会话 | 拆任务、派发、核对证据、维护一屏状态；可以读代码、跑检查；**不在无人复核的情况下执行生产变更** |
| 开发 | 开发智能体 | 实现功能 + 写测试；缺陷先写一个能失败的测试；**UI 和功能在同一张卡里完成** |
| 审查 | 审查智能体 | **必须开启终端工具**（能跑测试、看 diff），靠提示词约束"不改代码"；一次审查同时覆盖实现与测试真实性；只在 L1 及以上启用 |
| 页面验收 | 自动化优先 | H5 用 Playwright，小程序用 miniprogram-automator：打开页面 → 操作 → 断言 → 截图。AI 自测通过后，才请你做体验确认 |

小改动用一个会话 + CI 就足够。角色越多，重复执行和互相转述就越多，而不是越可靠。

## 2. 项目启动：Day 0 → Week 1

**Day 0（半天）**

- [ ] 一页产品确认书：要解决的问题、每个角色的 1 条核心旅程、必须具备、明确不做、成功标准（要写成可测量的）
- [ ] 唯一规则入口（TRAE 项目用 `.trae/rules/project_rules.md`，≤150 行），其他工具入口只写一行指向它（第 9 章）
- [ ] `CURRENT.md`（一屏）
- [ ] 远程仓库 + CI 骨架（lint + typecheck + test）当天跑绿，**对所有分支和 PR 生效**
- [ ] **平台约束调研**（第 3.5 节）：先查清楚目标平台哪些能力能用、要不要钱、有什么限制

**Week 1：行走骨架（walking skeleton）**

- [ ] 做一条最简陋但真实的旅程：页面 → API → 真实数据库 → 页面，部署到**验收环境**，用真实手机走通；**用每一个角色的账号各走一遍**
- [ ] 发布流水线：在 CI 或本机构建，产物带 git 版本号，一条命令发布，`/health` 返回版本号
- [ ] 第一个**系统不变量检查**（安全或数据完整性相关），能对生产库只读运行
- [ ] 第一条**页面自动化测试**（H5：Playwright 移动端视口；小程序：miniprogram-automator），会截图

骨架跑通之后，先做第 3 章的设计包和第 4 章的视觉对齐，再按用户旅程切片扩展功能。**不要先把后端和数据表铺满，最后才补前端。**

## 3. 开发前的设计包（先整体，后单页）

买菜平台真机发现的 19 个问题里，12 个是"整体设计没做"，5 个是"平台和部署约束没调研"，2 个是"验收只走正常路径"。下面这份设计包就是为了在写代码前把它们想到。**设计包由 AI 起草，你只确认"是不是我想要的"。**

### 3.1 整体导航图（你必须确认）

一张图回答：**每个角色打开应用后先看到什么？怎么找到"我的东西"？**

- 底部 tab / 首页入口按角色列出（双身份用户怎么切换）；
- 每个"对象"（如需求、报名、订单、投诉）的**列表在哪、详情在哪、从哪发起**；
- 消息 / 通知从哪看，点一条通知能跳到哪；
- 个人中心有什么（身份、认证状态、退出登录）。

### 3.2 角色 × 对象 × 动作矩阵

每个角色对每个对象：能不能**创建、找到、查看、修改、取消**，**每种状态下各自看到什么**。重点检查"对方操作之后，我还能不能看到"（例如商户确认后，报名不能从列表里消失）。

### 3.3 会话生命周期

首次登录、绑定手机、认证、切换角色、退出登录、登录过期、换设备——每一步屏幕上看到什么、失败怎么提示。**登录过期和网络错误必须分开提示。**

### 3.4 固定设计规则（每个项目默认生效）

1. **不让用户输入系统编号**（UUID、订单号、村庄编号）：一律从列表点选，或从相关页面带过去。
2. **每个按钮都要有反馈**：不能静默返回；未满足条件时说明缺什么。
3. **显示统一格式化**：枚举一律中文，时间一律"9月12日 06:00"这类本地格式，金额和单位统一，由一个公共函数负责。
4. **每个列表都有空状态、加载状态、错误状态**，错误状态有重试。
5. **表单任何操作顺序都不能丢已填内容**。
6. **所有请求走统一封装**：鉴权、过期、超时、网络错误、防重复提交在一处处理。

### 3.5 平台约束调研清单

写代码前逐项查清楚并记录（能用 / 不能用 / 要花钱 / 替代方案）：

- [ ] 登录与身份：微信登录、手机号快速验证（是否付费、是否限企业主体）、测试号与正式 AppID 的区别
- [ ] 域名：备案状态、小程序后台 request / upload / download 合法域名
- [ ] 网络：请求超时、上传 / 下载大小限制、代理层（nginx）请求体上限
- [ ] 文件：图片 / 视频格式、大小、转码；大文件是否需要分片或直传对象存储（不要把大文件 base64 塞进 JSON）
- [ ] 运行环境：最低微信版本、机型、字号放大
- [ ] 服务器：内存、是否与其他项目共用、构建在哪里做
- [ ] 部署配置：从代码里全量搜出所有环境变量，列成清单

### 3.6 验收场景清单（每个功能默认包含）

正常路径之外，至少覆盖：**反序操作、中途退出、快速连点、弱网 / 超时、登录过期、无权限、空数据、刷新重进、跨天**。

### 3.7 方案页面清单 → 任务对账

总方案里列出的每个页面，都必须对应到某张任务卡，或明确写"合并到哪一页 / 推迟到何时 / 取消（你确认过）"。**不允许页面静默消失。**

### 3.8 行为表按旅程写

V1.0 的行为表六项（场景、操作、屏幕、保存、刷新跨天、失败）保留，但按**用户旅程**组织（"商户发布一条需求，第二天看谁报了名并确认"），不按单个表单组织。

### 3.9 定稿后的变更

新想法先分类：原需求缺陷、新需求、UI 选择或技术内部调整。产品范围改变时说明影响，你确认后更新产品稿、导航图、UI 和测试；正常需求变更不算开发遗漏。

## 4. UI 与视觉

### 4.1 视觉对齐流程

1. **你给参考**：3–5 个你觉得好看、好用的同类应用截图，每张说一句喜欢哪里（颜色、图片、布局、字大、简洁……）。
2. **风格板**：AI 整理成一页（主色、辅色、字号、圆角、卡片风格、图片风格、信息密度），你确认或改。
3. **选组件库，不手写样式**：小程序优先 [TDesign](https://tdesign.tencent.com/miniprogram/) 或 [Vant Weapp](https://github.com/youzan/vant-weapp)；H5 选对应的移动端组件库。主题按风格板配置。
4. **视觉方向稿**：2–3 套，**差异在视觉**（配色、有无真实图片、卡片风格、密度），布局沿用已确认的导航图。每套只做 3 屏关键页面。
5. **在目标设备上看**：方向稿直接做成可运行的页面（小程序用开发者工具预览二维码，H5 给手机链接），**你在手机上看、点、选**，不在电脑浏览器里看静态稿做决定。
6. **用真实内容**：真实商品图片、真实中文、长文本和空数据都放进去，不用色块和字母占位。
7. **定稿**：覆盖正常、加载、空、错误、成功、无权限状态；设计令牌写进组件库主题配置，成为唯一来源。

"不能只换三种颜色"（V1.0 的规则）仍然成立——但它的意思是"方向之间要有实质差异"，**不是"不比较视觉"**。视觉和布局都要让你选。

### 4.2 实施与验收

- **UI 和功能同一张卡实施**。不要先在旧界面上做功能、再整体换皮。
- 每页实施后，自动化工具截图，和定稿并排放在一页里发给你，**一次收集意见**。
- 视觉问题集中改，不按单个意见各开一轮真机测试。
- 不写"断言 wxml / html 里必须有某个字符串"的测试，它会把页面结构焊死；用页面自动化测试断言屏幕上看到的内容。

### 4.3 不要做的事

- 不让写代码的 AI 在没有参考的情况下自己定配色和风格。
- 不在"功能零增减、只重排"的约束下做重新设计——那只是换皮。
- 不用电脑浏览器里的静态稿代替手机上的真实效果。

## 5. 风险分级：流程强度只由这张表决定

| 级别 | 典型改动 | 必须做 | 不必做 |
|---|---|---|---|
| **L0** | 文案、间距、注释、补测试、脚本参数、文档 | CI 绿；UI 类改动附自动化截图 | 任务卡、evidence 文件、独立审查 |
| **L1** | 普通功能、普通缺陷修复 | 半页任务卡；缺陷先写失败测试；CI 绿；**一次**可执行命令的独立审查；受影响的页面自动化测试通过并截图 | 多份报告、多个角色重复跑同一套命令 |
| **L2** | 契约或数据结构、迁移、推荐或计算逻辑、安全规则、鉴权与会话、缓存与部署配置、导航结构 | L1 全部 + **影响清单**（见下）+ 真实数据库集成测试 + 不变量检查 + 在验收环境预演 | — |
| **L3** | 生产数据变更、发布、删除、不可逆操作、涉及费用 | L2 全部 + 备份 + 可回滚脚本 + 你的授权 + 发布后冒烟 + OPS-LOG 记一行 | 手工敲命令 |

**升级规则**：拿不准时升一级；用户反馈的缺陷至少按 L1；任何触及"安全红线"的改动至少按 L2；紧急修复可以先修，但 24 小时内要补齐对应级别的检查。

**L2 影响清单**（每项回答"是 / 否 + 怎么验证"）：

1. 会不会改变已有数据的含义（ID、枚举、外键、快照）？
2. 历史数据、学习和统计链路是否仍然正确？
3. 安全不变量是否仍然成立？
4. 生产数据与本地数据的差异，会不会让验证结论失效？
5. 前端要不要同步？缓存会不会让用户拿到旧版本？
6. 回滚之后，数据是否兼容？

## 6. 完成的定义与质量门禁

### 6.1 完成的五层（只能逐层前进）

| 层 | 名称 | 达成条件 |
|---|---|---|
| 1 | 已实现 | 代码和测试在分支上，CI 绿 |
| 2 | 已验证 | 审查通过、不变量通过、页面自动化测试通过并有截图 |
| 3 | 已发布 | 生产版本号等于该提交；发布后冒烟通过 |
| 4 | 用户确认 | 你按体验卡走过了核心任务 |
| 5 | 效果达成 | 测到了成功指标（例如一周的真实使用数据） |

向你汇报时必须说明处于第几层。"本地通过"只算第 1–2 层，不能说成"已修复"。**第 2 层没有达到时，不请你做真机测试。**

### 6.2 质量门禁（必须机器化）

- [ ] lint + **全包** typecheck（包括前端和测试文件）
- [ ] 纯逻辑单测
- [ ] 真实数据库集成测试，迁移要验证两条路径：**从空库**建和**从上一版本升级**
- [ ] **系统不变量检查**：安全与数据完整性相关，同时能对生产只读运行
- [ ] 生产构建 + 产物检查：不含本机地址、不含密钥或口令
- [ ] **页面自动化测试**：每个角色 3–5 条核心旅程，移动端尺寸，自动截图
  - H5：Playwright（TRAE 可接 Playwright MCP）
  - 微信小程序：[miniprogram-automator](https://developers.weixin.qq.com/miniprogram/dev/devtools/auto/)（开发者工具开启自动化端口，如 `cli auto --project <目录> --auto-port 9420`；截图在模拟器中进行，真机体验仍需你确认）

**不进门禁**：墙钟性能阈值（改成基准测试，只报告不阻断）；需要人工判断的视觉效果（用截图对比，或交给你体验）。

**禁止**：失败了就重跑直到偶然通过；跳过或弱化测试来换取通过；把构建产物提交进仓库来绕过构建；用手写夹具证明"安全"（安全必须对真实数据再检查一遍）；只检查"文件存不存在"就叫前端验证通过。

**系统不变量举例**（每个项目挑 3–5 条，写成可执行检查）：任何对用户可见的内容都不违反硬性规则（忌口、权限）；用户反馈作用在正确的对象上；规则引用的对象真实存在；对方操作后，相关角色仍能看到自己的记录；页面最后一个操作按钮完全可见；生产产物里没有本机地址和口令。

## 7. 发布与生产操作

- **验收环境与正式环境分开**：至少分开数据库和后端进程；测试数据只在验收环境造和删。前端按环境切换接口地址（小程序可用开发版 / 体验版 / 正式版区分），不写死。
- **在 CI 或本机构建，不在生产机上构建。** 产物推送到镜像仓库或上传成品，生产只负责拉取和启动。
- 产物 tag 等于 git 提交号；生产能直接查询到当前版本。
- 数据库迁移作为独立步骤，**先于**新版本启动；迁移只做加法。
- 前端入口 HTML 不缓存，带哈希的资源长缓存；**缓存策略只在一层代理里配置**。
- 生产上实际生效的全部配置（代理、进程管理、systemd）都要入库，并由部署脚本下发。
- 生产数据变更一律写成"备份 → 执行 → 校验 → 回滚"四段式脚本并入库，**执行前由另一个角色复核**。
- **多个项目共用一台服务器时，在每个项目的 CURRENT.md 里登记**（内存、端口、谁会影响谁）。
- 发布后自动冒烟：版本号、核心 API、核心旅程、不变量检查。
- 工具或沙箱挡住了标准操作时：**停下来修环境，或请你来执行**。不要手工伪造系统状态（手写迁移记录、手改 checksum）。

## 8. 缺陷处理（沿用 V1.0 第 8 章，强调五点）

1. 先在与你相同的条件下复现：同样的设备、版本、数据和缓存状态。
2. 修复必须留下一个在修复前会失败的检查。
3. 同一现象第 2 次交付仍未解决：停止叠补丁，换干净上下文做根因复查。第 3 次：由你决定是否换方案。
4. 你说"还是不行"时，默认上一轮结论是错的，优先怀疑数据、环境、缓存和版本，而不是代码逻辑。
5. **AI 给你的任何操作指引（"点哪里、填什么"），必须先在实际页面（截图或自动化）上核对过**，不凭代码推测页面长什么样。

## 9. TRAE CN 落地

依据：[TRAE 规则文档](https://docs.trae.cn/ide/rules)、[TRAE 智能体文档](https://docs.trae.cn/ide/agent)。工具功能会变，采用时以当时文档为准。

### 9.1 规则放在 TRAE 读取的位置

- **`.trae/rules/project_rules.md` 是唯一规则入口**（TRAE 自动加载），≤150 行：项目一句话、架构地图、常用命令、红线、风险分级表、设计规则。
- TRAE 可以开启"读取 AGENTS.md / CLAUDE.md"。如果开启，这两个文件**只写一行指向 project_rules.md**，避免新旧规则同时进入上下文；不需要就关闭开关。
- 不要放其他工具格式的配置当作规则（例如 `.codex/agents/*.toml`，TRAE 不读取）。
- 换规则时**替换**旧文件（旧的移入 `docs/archive/`），不叠加。改完后开一个新会话，问它"现在的规则是什么"，确认读到的是新规则。

### 9.2 智能体提示词入库

- 开发、审查、验收三个自定义智能体的提示词各存一份到 `docs/agents/*.md`。**改提示词先改仓库，再粘贴到 TRAE**；换项目时从仓库复制，不凭记忆重建。
- 每个智能体的提示词只写角色差异；所有智能体都要遵守的规矩写在 project_rules.md（智能体提示词之间不共享）。
- **审查智能体要开启终端工具**，否则只能读代码、不能跑测试，命令又落回主控身上。

### 9.3 让 AI 能看到页面

- H5：为验收智能体配置 Playwright MCP 或 Playwright 脚本。
- 小程序：在微信开发者工具中开启自动化 / 服务端口，验收脚本用 miniprogram-automator 连接、操作、截图，截图存入 `evidence/`。
- 第一次建流程时就验证"AI 能否打开页面并截图"，**这一项不通过，不开始写页面**。

### 9.4 会话与并行

- 一个仓库同一时间只有一个会话在写同一工作区。确实要并行时，每个会话用自己的分支（或独立工作区），通过合并集成。
- 长任务中途上下文被压缩时，以仓库文件为准恢复（project_rules → CURRENT → 当前任务卡），不依赖对话摘要。
- 状态同步（例如 CURRENT.md 更新提交号）**和对应的代码提交合并成一次提交**，不单独提交。

## 11. 节奏、挂账与你的负担

### 11.1 挂账与节奏

- 挂账上限 10 条，按"对用户的价值 × 风险"排序；每周清理一次，低价值的直接关闭。
- 审查的"建议级"意见默认不进挂账，只有阻断级和风险级才立卡。
- **不给无边界的授权**。授权要写清范围和终止条件，例如："做完 X 为止，或累计 5 张卡后停下汇报"。
- 每个切片结束时问一句："这件事你能感受到吗？"连续 3 张卡都不能，就停下来和你重新对齐方向。

### 11.2 与你的决策协议

- 问"要不要、选哪种体验、喜欢哪种样子"，**不问"用哪种技术方案"**。
- 每个问题附上：一句话背景、每个选项的代价、AI 的推荐、默认做法。
- 你跳过 = 采用默认做法；但**安全、费用、生产数据、不可逆**这四类不能默认，必须等你明确答复。
- AI 主动提出应该问你的事：安全暴露、批量改动线上内容、任何可能影响真实用户的操作。

### 11.3 减轻你的真机测试负担

- 只有第 6.1 节"第 2 层已验证"（含自动化截图）之后才请你真机测试。
- **攒一批再请你测**：一次体验卡覆盖多个改动，写清每项"做什么、应该看到什么"。
- 你反馈的问题，AI 先复现并截图确认理解一致，再修。

## 14. 反模式清单（每条都在两个项目中真实发生过）

| 反模式 | 当时的后果 |
|---|---|
| 分层逐个验收，最后才拼起来 | 家庭菜谱 230 个绿灯核心全不可用；买菜平台"MVP 全部完成"后首次真机，认证用户进不了任何角色功能 |
| 行为表按功能写、没有整体导航图 | 商户找不到自己的需求、农户看不到自己的报名、草稿找不到、确认后报名消失 |
| 方案页面清单不和任务对账 | "我的供货 / 消息中心 / 个人中心"静默消失，两个月后以缺陷形式回来 |
| 让用户手输系统编号 | 填村名直接 500；交付编号全端找不到 |
| 平台约束不调研 | 手机号组件是付费能力、测试号不能上传、大视频 base64 超时 |
| 视觉风格不问用户，方向稿只比布局 | 两个项目的 UI 都被推翻或不满意 |
| 功能零增减的"换皮式"重设计 | 首页仍是按钮菜单，角色和缺页问题不在范围内 |
| AI 看不到自己做的页面 | 你做了约 14 轮真机复测，是唯一的页面验收员 |
| 没看过页面就给用户操作指引 | "随便填个村名""点列表选中"两次误导 |
| mock 测试冒充可用性；夹具证明安全 | "禁忌集 100%"时真实规则拦截 0/49 |
| 规则通过环境相关的 ID 引用数据 | 生产过敏规则悬空约 8–9 小时 |
| 口令编进前端 | 公网等于不设防 |
| 验收环境就是正式环境 | 在生产库里造测试数据、关触发器删数据 |
| 在生产机上构建、两个项目共用未登记 | 3 次 OOM、1 次全站 502，影响面说不清 |
| CI 配置在但没有远程仓库 | 文档称"CI 执行数据库门禁"，实际从未运行 |
| 两层代理、两套缓存；每页魔法数布局 | "改了没生效"修 3 轮；底栏遮挡修 6 轮 |
| 构建产物入库；失败重跑到通过 | 陷阱反复出现；门禁失去意义 |
| 规则放在工具不读的位置；智能体提示词不入库 | 新会话读到废止规则；换项目只能凭记忆重建角色 |
| 状态文件写成流水账、每次同步单独提交 | 86% 的提交只改文档；审查原文被上下文压缩丢失 6 次 |
| 严格流程只用在小事上 | 2 个断言走四角色，12 文件的生产修复零流程 |
| 无边界授权；让非程序员选技术方案 | "跳过=推荐"成惯例；约 30 张卡消化流程自身的问题 |
| 工具受限时伪造状态绕行 | 手写迁移记录引出 3 张修复卡 |

## 15. 在已有项目上采用本流程的步骤

1. **规则入口**：合并为唯一的 `.trae/rules/project_rules.md`，旧入口移入 `docs/archive/`；智能体提示词入库；新会话验证读到正确规则。
2. **CI**：建远程仓库，对所有分支和 PR 运行并变绿；把散落的回归脚本纳入测试。
3. **看得见页面**：打通页面自动化截图（第 9.3 节）。
4. **设计包补课**：画整体导航图、做方案页面对账、列平台约束和设计规则违例清单（手输编号、英文直出、静默按钮）。
5. **环境**：分开验收与正式环境；生产打上版本号，一条命令发布、一条命令回滚；登记共用资源。
6. **不变量与旅程**：写出 3–5 条系统不变量检查和每个角色 3 条旅程测试，并对生产只读跑一次。
7. **一屏状态**：CURRENT.md 重写成一屏，历史移入 CHANGELOG。
8. **按级执行**：从下一个任务开始按风险分级执行；两周后看第 12 章的指标，再做一次减法。
