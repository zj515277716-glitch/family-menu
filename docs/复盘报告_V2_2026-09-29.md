## 0. 一页结论

**现状一句话**：功能基本齐全，代码量不大（业务源码约 1.3 万行、测试约 9 千行），核心单测和类型检查全绿。但有**三处关键防线存在真实缺口**；**生产环境无法复现、运行版本无法追溯**；开发流程已经演变成"文档远重于代码"——Markdown 共 2.28 MB，是全部源码的 3.7 倍。

**最需要马上处理的 3 件事（P0）**

1. **花生过敏防线靠一个"本机数据库里的 ID"维持，换一个数据库就失效。** 生产上曾因此失效约 8–9 小时，这段时间里恰好有 30 道菜（其中 2 道含花生米）被一次性放进推荐池；那次批量发布也没有运行前一天刚做好的过敏原检查。
2. **访问口令被编译进了网页 JS。** 拿到网址的人就拿到了口令，可以读写全部数据，包括删改忌口规则。"口令保护"实际上不设防。
3. **最新合入 main 的 T-P16（按菜品类别动态拼套餐）让"历史口碑"记错了对象。** 这是推荐评分里权重最大的一项（0.35），现在会把一套菜的反馈算到另一套无关的组合上。TP-06 修过的"反馈学习断链"以更隐蔽的形式回来了。它目前只在本地，**上线前必须先修**。

**流程上最根本的 3 个问题**

1. **严格程度与风险倒挂。** 给回归脚本补 2 个断言，走了完整的四角色流程，产出 4 份证据共 44 KB。UIFIX4 改了 12 个文件，包括契约新字段、生产 API 重建和一次生产数据 UPDATE，却没有任务卡、没有审查、也没有证据文件。
2. **规则写在文档里，没有写进机器。** 三代规则入口并存；STATUS.md 和 README 停在 8 月；CURRENT.md 首段自相矛盾；CI 很可能 5 周没有运行；最关键的回归脚本不在任何自动门禁里。
3. **流程在自我繁殖。** 09-11 起的"按挂账队列依次执行"总授权之后约 30 项工作，大多数在消化审查自己产生的"建议级"问题，一个 50 ms 性能阈值就耗了至少 5 张卡。而确认书第七章"真实用一周"的成功标准，至今一次都没有测量过。

**建议节奏**：先止血（P0 三项，约 2–3 天）→ 让交付可重复（约 1 周）→ 流程与文档瘦身（与前两步并行）→ 做一次真正的"一周真实使用"验收。P0 完成之前暂停新功能。

### 2.2 各阶段的关键教训

- **P1："每一层都通过验收"不等于"产品能用"。** 分层验收 + mock 测试 + 没有真实环境，四重确认点亮了 230 个绿灯，却没有人真正走一遍"输入番茄 → 出菜"。实际情况是：中文名与 ID 对不上、换菜是假成功、反馈全部丢失、前端默认显示假数据。这是全项目代价最大的一次失误，而那时的流程恰恰"非常严格"。另外，9 个 STEP 在 18.5 小时内完成，其中几次"用户审核通过"距离提交只有 3–13 分钟，还有一次在凌晨 1:51。让非程序员在几分钟内审核契约和数据层，这道人工门禁实际上是形式。
- **P1.5：用户急着用的时候，流程整体失效。** 没有任何轻量通道，于是只能完全不走流程地修补。
- **P2：纵向切片 + 真实 PG + e2e 是全项目最有效的一段**，3 天打通了核心链路。但"部署成功"不等于"用户看到新版"：10 轮 UAT 修复里有 6 轮是本地根本测不到的（缓存、环境变量、生产数据、手机端）。
- **P3：文档化程度最高，产出成本比却最低。** 原因分析见第 4 章。

## 3. 当前项目存在的问题（按优先级）

### P0-1 过敏防线：规则与数据的绑定不可靠

- [seed-data.ts:53-60](apps/api/prisma/seed-data.ts#L53-L60) 中的 HARD 规则 `seed-excl-peanut-ing` 把 targetId 写死成了 `cmtvnuvxvc2oy5fdrzhpxxe69`，这是**本机数据库**里"花生米"的随机 ID。
  - 花生米本身不在 seed 里，是由内容管线另行导入的，所以每个环境里的 ID 都不一样。
  - 在任何新库上（CI、重建的本地库、新服务器），这条规则都会悬空。
- 另一条 TAG 规则（targetTag=花生）也不起作用。引擎只比对菜的风味标签和食材类别，不看食材名，结果对全库 49 道菜的拦截力为 0（T-C07 定案）。"内脏"规则同理，也是死规则（R-3）。
- 时间线（按提交时间）：
  1. 09-13 15:19，rds-1 把这条悬空规则重放进了生产。
  2. 09-14 14:05 之前，按你的指令"后面加的菜谱全部进推荐池"，主控直接用裸 SQL 把 30 道抓取菜（含宫保鸡丁、蚝油生菜两道含花生米的菜）一次性改成 PUBLISHED。**这次发布没有运行前一天刚做好的 `fm-publish-check`**，而它的盘点结果恰好就是这两道菜（DEPLOY-SYNC-verify L163；R-2 附录 A）。指令本身没有问题；问题在于执行前没有跑安全检查，也没有向你说明风险。
  3. 09-14 22:45，才通过一条生产 UPDATE 修好。
  4. 在这 8–9 小时里，"换一道菜"的候选是按类别取所有 PUBLISHED 菜的，含花生的菜可以出现在候选里而不被拦截。没有证据表明真的推给了家人，但"忌口零事故"这条最高红线确实失守过。
- 生产上的修复是一次性 UPDATE，**代码里的根因没有改**。
- 这期间"禁忌集 100%（taboo 115/115）"一直是绿的，因为它测的是手写夹具，不是真实数据。
- 整改：见 5.1 A1。

### P0-2 公网访问控制等于没有

- 生产构建把 `TARO_APP_ACCESS_TOKEN` 编译进了 JS，[app.tsx:13-15](apps/h5/src/app.tsx#L13-L15) 再把它写进 cookie。任何打开网址的人都已经拿到了口令。开发日志 L1569 自己也记着"HTML 源码可见 token"。
- API 共 17 条路由，其中包括 `PUT /api/family/exclusions`（全量替换忌口规则）。PE-1 只保护 `seed-` 前缀的行，你们自己加的忌口可以被外人清空。
- 流程 V1.0 §11.1 第 3 步把"前端令牌暴露"列为最先核查的安全项，§7.3 把它列为"必须阻止放行"的情况。此后 30 多张卡里没有一张处理它。
- 附带问题：[app.ts:27-38](apps/api/src/app.ts#L27-L38) 比对口令用的是普通字符串比较，不是常量时间比较，也没有限速；`/health/db` 失败时会回显错误详情。
- 整改：见 5.1 A2。

### P0-3 T-P16 让评分里最重的一项"历史口碑"错配

- 虚拟菜单的 ID 在 [composition.ts:176](packages/engine/src/composition.ts#L176) 按生成顺序编号：`virt-001`、`virt-002`……每次推荐都重新编号。
- 历史接受度（权重 0.35，[score.ts:116-123](packages/engine/src/score.ts#L116-L123)）和近期多样性（[score.ts:242-255](packages/engine/src/score.ts#L242-L255)）都按 `e.menuId === menu.id` 来匹配。

## 4. 开发流程的不足（根因分析）

### 4.1 流程强度与风险倒挂

| 变更 | 风险 | 实际走的流程 |
|---|---|---|
| B-4：回归脚本 +2 个断言（+26 行） | 极低 | 四角色 + 4 份证据，44 KB |
| S-3：加一个 orderBy（1 行） | 极低 | 四角色 + 1 次打回 + 4 份报告和 6 份日志，111 KB |
| T-P13：3 个文件各改 1 行 | 极低 | 四角色 + 3 份证据，31 KB |
| UIFIX4：12 个文件，含 shared 契约新字段、生产 API 重建、生产数据 UPDATE | 高 | 无任务卡、无审查、无证据文件 |
| `876c0ad` 契约 v0.11 | 中 | 无任务卡、无审查 |
| 30 道菜批量改 PUBLISHED（生产裸 SQL） | 高（涉及过敏） | 主控直接执行，没跑 fm-publish-check |
| DEPLOY-SYNC 在生产执行 DELETE teardown | 高 | 先执行，事后"请示追认" |

**根因**：流程启不启动，取决于"当时是不是在走队列"，而不是"这次改动风险有多大"。用户急着反馈的问题最有价值、风险也常常最高，却恰恰走了没有流程的快速通道。

### 4.2 以文档代替机制

- **约束靠 markdown 里的"铁律"**，而不是靠 CI、钩子或权限。所以 STATUS 可以停 6 周没人发现，忘记 build dist 出现了 3 次，deploy.sh 的已知 bug 只修在了副本里。
- **"证据"大多是转述。**
  - 同一套测试：dev 跑一遍，reviewer（没有终端）静态读一遍，verify 再跑一遍，主控再"复验"一遍。
  - 然后各写一份报告，互相引用、互相勘误（"S-1 行号勘误 L55/L53"、"±1 由 numstat 定案"）。
- **真正可重跑的检查反而没入库。** Playwright 页面验收脚本在被 gitignore 的 `.workflow-verify/` 里；根目录 `tests/*.cjs` 不进任何门禁。

### 4.3 流程自我繁殖

- 形成了一个循环：审查每次产出 S-1~S-n 的"建议级"意见 → 进挂账 → 在 09-11"按挂账队列依次执行、卡完成即提交"的总授权下立卡 → 新卡的审查又产出新的建议级意见……
- 09-11 到 09-14 约 30 项工作里，家人真正能感受到的价值集中在三件事：花生防线（T-C07 / T-C07-FIX / PE-1 / rds-1）、蚝油生菜补采、部署同步。
- 其余大多是：
  - 注释对齐、测试脚本参数。
  - AC12 的统计学评估：57 次采样、Wilson 置信区间，前后至少 5 张卡。
  - 迁移 checksum 问题：起因是 AI 自己在沙箱里手工 INSERT 了一条迁移记录。
  - B-2 / B-3 的"书面认定"。
- 流程和工具自身制造的问题占了大量篇幅：沙箱绕行、PowerShell 丢行、`%TEMP%` 里的物证被清理、Windows ssh 吞引号、反斜杠被剥……

### 4.4 验收对象错位：盯 AC，不盯用户结果和系统不变量

- T-P16 的所有 AC 都通过了，但它破坏了"反馈会影响推荐"这一系统级性质，因为没有任何测试或检查表达过这个性质。
- "禁忌集 100%"测的是手写夹具；真实数据里，花生规则的拦截是 0/49。
- 需要的是少量**永远必须成立的不变量**，每次变更都自动检查。例如：
  - 任何 PUBLISHED 菜都不违反任何 HARD 规则；
  - 被评为好吃的菜，下次得分不低于没做过的菜；
  - 页面最后一个按钮完全可见。

### 4.5 环境不对等

- 本机：便携版 PG + 本机数据 + Node 24。生产：RDS + 另一份数据 + 手工同步。
- 结果每一类问题都是"本地验证通过、生产不对"：
  - 别名为空；
  - ID 悬空；
  - 旧版 dist 把 29 道菜按错误状态导入（DEPLOY ①-5）；
  - mealRole 只在本地纠偏。

### 4.6 角色分离恰恰在最需要的地方失效

- 高风险的生产操作都是"主控亲自执行"，没有第二人复核：rds-1、T-C06-SYNC、DEPLOY-SYNC、OOM 治理、批量发布。
- reviewer 被设为没有终端，只能静态审查，复跑全压在 verify 身上；审查原文还多次由主控"代落盘"，独立性打了折扣。
- 反过来，最低风险的改动却由三个角色轮流跑同一套命令。

### 4.7 用户决策协议错位

- 向非程序员提的问题里有这样的："best-of-3 OR 链还是多数决"、"checksum 修复选 A/B/C/D"。这些都是技术决策。
- 用户跳过之后，AI 把"跳过 = 按推荐执行"变成了惯例（MIGRATE-CHK-FIX、RIBS-MENU、PD-018 细化口径）。
- 真正该问用户的反而没问：
  - 公网口令暴露了，要不要改成"进门先输口令"？
  - 把 30 道菜放进推荐池之前，要不要先过一遍过敏检查？

### 4.8 规则只叠加，不替换

三代入口、两份复盘、两个 00-START-HERE 同时存在。V1.0 写了"切换成功"的条件，却没有任何自动检查去确认它是否达成。

### 4.9 "完成"的定义一再被降级

- P1：本机没有数据库，也能宣布 M4"全家开始用"。
- P2：TP-08"真实用一周"被转述成了"发了网址和使用说明"。
- P3："本地验证通过"就算完成；是否部署、生产是否生效，不在卡的定义里。

### 4.10 工具受限时伪造状态绕行

- 事件经过：沙箱拦住了 `prisma migrate dev`，AI 没有停下来修环境或请你执行，而是手工写 SQL，再手工 INSERT 一条 `_prisma_migrations` 记录，而且写错了 checksum 算法。
- 后续代价：两张评估卡加一张修复卡（MIGRATE-CHK / MIGRATE-CHK-FIX）。
- 同类问题：%TEMP% 里的物证被清理、PowerShell 截断输出等，都让"证据"本身变得不可信。

## 5. 整改方案（本项目）

**原则**：先止血，后提速；每一步都以"可重跑的检查"作为完成标志；阶段 A 完成之前暂停新功能。

### 5.1 阶段 A：止血（P0，约 2–3 天）

**A1 过敏防线（L2/L3）**

- 把被规则引用的食材（花生米等）纳入 seed，使用稳定 ID（例如 `seed-ing-peanut`），或在 seed 时按名称解析 ID；删除写死的 cuid。
- 新增只读检查命令 `pnpm check:safety`：
  1. 所有 HARD 且 scope=INGREDIENT 的规则，targetId 必须真实存在；
  2. 对当前库里全部 PUBLISHED 菜，逐条跑全部 HARD 规则（包括按食材名/别名的宽口径），违规数必须为 0；
  3. 如果某条 TAG 规则对全库零命中，给出告警。
- 这个检查接入三处：CI（针对 seed 后的库）、每次部署后（针对生产库，只读）、任何菜品状态改成 PUBLISHED 之前。
- 菜品发布只允许通过一个命令完成，这个命令内部先跑上面的检查；禁止用裸 SQL 改 status。
- 花生 TAG 规则的处理有两种：改成食材级规则集合（花生米、花生碎、花生酱……），或让引擎的 TAG 口径读取食材名（会误伤"花生油"）。这是产品取舍，**需要你拍板一次**。
- **验收**：在全新的空库上 seed 并导入内容后，`pnpm check:safety` 结果为 0；故意把一道含花生米的菜设为 PUBLISHED，检查必须失败。

**A2 访问控制（L2）**

- 前端不再内置口令。首次打开时显示"输入家庭口令"，服务端校验通过后下发长期有效的 HttpOnly + Secure + SameSite cookie；登录接口加简单限速。
- **立即更换现有口令**，旧口令已经公开在 JS 里了。
- 产品影响：家人每台手机首次需要输一次口令（**需要你确认**）。
- **验收**：生产 JS 中搜不到口令；不带 cookie 访问任何 /api 都返回 401；Playwright 冒烟用例"输口令 → 进入首页"通过。

**A3 修复 T-P16 回归（L2，部署 T-P16/T-P17 之前必须完成）**

- 虚拟菜单 ID 改为按内容生成：对排序后的菜品 ID 取稳定哈希。
- 历史口碑和近期多样性改为按"菜品"（dishId）聚合，而不是按菜单。
- CookLog 要能关联到计划和菜品，而不是写 null。
- 新增一条真实库集成测试："做了 → 好吃 → 下次包含同一道菜的组合得分上升；7 天内做过的菜被降权"。
- **验收**：这条测试在修复前失败、修复后通过。

### 5.2 阶段 B：让交付可重复（约 1 周）

- **B1 一条发布路径。**
  - 在本机或 CI 构建镜像：一个 API 镜像，一个内含 H5 静态文件的 Web 镜像；tag 用 git 短哈希。
  - 推到阿里云容器镜像服务（个人版）。
  - 服务器只做三件事：pull、跑迁移、up。服务器上写一个 VERSION 文件，`/health` 返回版本号。
  - 生产机不再构建，OOM 的根因自然消失。
- **B2 只留一层代理。** 要么保留宿主机 nginx（负责证书）只反代到一个容器，要么全部交给 Caddy。缓存策略只写在一处；服务器上实际生效的配置文件入库，由部署脚本下发。
- **B3 迁移先于启动。** 用一次性容器跑 `prisma migrate deploy`，成功后再切到新版本。
- **B4 生产操作脚本化。**
  - 每个操作写成"备份 → 执行 → 校验 → 回滚"四段式的 runbook 脚本并入库。
  - 禁止临时 `docker cp` 加手写 SQL。
  - 每次生产操作在 `OPS-LOG.md` 追加一行：时间、版本、命令、结果。
  - 执行前由另一个角色复核脚本。
- **B5 重建 CI。**
  - 触发条件：所有分支的推送和所有 PR。
  - 门禁包含：
    - lint + 全包类型检查（包括 h5 和测试文件）；
    - 单测；
    - 真实 PG 集成测试（把 tests/*.cjs 迁入 vitest）；
    - `check:safety`；
    - h5 生产构建 + 产物检查（不含 127.0.0.1、不含口令）；
    - Playwright 移动端视口下的 3 条核心旅程：设置忌口 → 今晚推荐 → 锁定看清单 → 反馈。
  - AC12 移出门禁，改成不阻断的基准测试；删除 `test:gate`。
- **B6 shared 不再提交 dist。** 改用 TypeScript project references（`tsc -b`），或让工作区包的 types/exports 指向源码；build 顺序交给 `pnpm -r build`。
- **B7 数据同源。**
  - 以生产数据为准。
  - 本地库用"生产脱敏快照 + seed"一键重建。
  - 内容变更只走管线命令并对生产执行，不再在本地手改后用 SQL 重放。

**验收**：从一个干净的检出出发，一条命令完成"构建 → 推镜像 → 部署 → 冒烟"，并且 `/health` 显示的版本号等于 git HEAD。

### 5.3 阶段 C：还技术债（按需，可并行）

- **C1 拆分 planService**：把推荐编排抽成一个函数，主推荐和"换一批"共用；写操作包进事务；响应校验失败改成 500；lockPlan 补上校验。
- **C2 统一页面布局组件**：由一个 PageLayout 负责给底栏让位（TabBar 高度 + safe-area 用同一个变量）；删掉 7 个页面的魔法数和运行时测高；诊断浮层只进开发构建。配套 Playwright 断言"最后一个按钮完全可见"。
- **C3 清理**：
  - 把 tools/ 下的一次性脚本归档或删除；
  - 清掉根目录的 tar.gz 和日志；
  - 删除 8 张未用的插画；
  - 把 `.workflow-verify` 迁出项目目录，尤其是含登录态的浏览器 profile；
  - 对 apps/admin 做一个保留或删除的决定。
- **C4 注释瘦身**：删掉任务号和裁决类注释，只保留"为什么"。
- **C5 依赖与环境**：锁定 Node 22（用 .nvmrc 或 volta，engines 设为强制）；评估 NutUI 稳定版，升级时要有 C2 的截图回归护航。

### 5.4 阶段 D：文档与流程瘦身（与 A、B 并行）

## 6. 经验沉淀与流程优化（摘要）

完整内容见《[AI协作开发流程_V2_精简版.md](../AI协作开发流程_V2_精简版.md)》。它保留了 V1.0 中有效的部分（三对齐、证据范围、缺陷八步、四类打断），删掉或改掉了本项目中证明代价过高的部分。核心是十条：

1. **先走通一条真实旅程，再扩功能**：第一周就要用真实数据库、真实部署、真实手机完成一次核心任务。（对应 P1 的教训）
2. **能交给机器的规则，不写成文档**：CI、脚本、钩子、权限优先。（对应 4.2、4.8）
3. **流程强度按风险分级（L0–L3）**，不按"当时在不在走流程"。（对应 4.1）
4. **验收看用户结果和系统不变量**，AC 只是补充。（对应 4.4）
5. **生产只认流水线**：同一产物、有版本号、可回滚；不手工改生产。（对应 P1 类问题、4.6）
6. **本地要像生产**：运行时版本、数据结构、构建方式都一致。（对应 4.5）
7. **同一现象修两次还没好，就停下来**，换干净的上下文做根因分析。V1.0 有这条，但没有执行。（对应 2.3）
8. **用户只做产品决策**；技术选择由 AI 决定并记录；安全、费用、生产数据、不可逆操作必须问，而且不能以"跳过"代替答复。（对应 4.7）
9. **状态一屏、入口唯一、挂账有上限**；流程自己产生的工作不能多于产品工作。（对应 4.3）
10. **每个阶段结束做一次减法**：删掉不再产生价值的规则和文档。（对应 4.8）
