## 2. 四角色与承担者

| 角色 | 承担者 | 允许 | 不允许 |
|---|---|---|---|
| 主控 PM | SOLO 主会话（不另建 PM Agent） | 读项目与证据、派发任务、维护状态、汇总给用户 | 写业务代码；批准自己的技术实现；降低验收要求 |
| 开发 DEV | fm-dev（TRAE 智能体） | 改被授权代码、加测试、隔离环境自测 | 自己批准交付；顺手扩功能；删测试换通过 |
| 技术审查 REVIEW | fm-reviewer（TRAE 智能体，工具级只读：关写入/编辑/终端） | 独立读需求与代码、复跑检查、提出可复现问题 | 改业务代码；只复述开发报告 |
| 产品验收 VERIFY | fm-verify（TRAE 智能体） | 真实页面操作、截图/轨迹、验收测试、脱敏证据 | 接口返回冒充页面结果；生产造数据；改 UI 基准 |

- 角色行为规则以流程文档为准：12.3（主控）/ 12.4（开发）/ 12.5（技术审查）/ 12.6（产品验收）。
- 按需专家：fm-arch / fm-ui / fm-tester 按需调用，不常驻（流程文档 3.1）。
- 任务经交接卡派发（流程文档 12.7），成员按 12.8 回报；主控按流程文档第 6 章步骤 5 核对放行。

## 3. 调度与写入纪律（摘要，全文见流程文档 3.2）

1. 一个项目只有一个主控维护当前队列；默认只有一个活动业务代码任务（WIP=1）。
2. 两个角色不得同时修改同一工作区的同一批文件。
3. 成员向主控返回发现和建议，不自行给其他成员派活。
4. 审查后代码再改动，受影响的审查与测试结论必须更新。
5. 运行时代码禁止调用任何 LLM API；不引入 Redis / 消息队列 / 微服务 / K8s。

## 4. 状态与用户可见口径（流程文档 7.4）

- 内部验证通过 → 用户看到"可体验"；发布条件具备 → "可上线"；两者都不是"已上线"。
- "内部验证通过"不等于用户确认，也不等于上线授权。
- 一周真实使用等效果验证另记"观察中"，不混入代码完成状态。

## 5. 只在四种情况打断产品负责人

1. 产品含义有两种合理解释且影响结果；
2. UI 或操作体验需要选择；
3. 需要账号、费用或外部平台权限；
4. 生产数据、对外发布、删除、不可逆操作或超出已有授权的风险。

一次只问一个最关键的问题，用普通中文。

## 6. 当前试点与能力验证状态

- 试点用户流程：**「必消食材输入 → 推荐结果」**（含空手场景）。任务卡随试点建立于 `docs/workflow/tasks/`。
- 能力验证（流程文档 3.3）未全部通过前，不进入正式开发；每项结论标注"已验证／不支持／未验证"。

## 7. 每次开工核对（上下文恢复）

- 我是谁，负责哪项任务？
- 产品与 UI 依据是哪个版本？
- 目标、禁止范围、完成条件是什么？
- 当前代码与上次检查结果是什么？
- 哪些仍是推测或未验证项？

不凭日志最后一句"继续"开工；发现入口互相矛盾，先报告主控整理指向，不沿用最方便的一份。
