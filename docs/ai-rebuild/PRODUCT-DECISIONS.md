## 明细

### PD-001 必消食材 = 硬要求
- **问题**：用户在今晚页输入必消食材（如"番茄"）后，系统把它当什么？
- **候选**：硬要求（用不上的方案不出现，实在没有就明说）／ 尽量用上（卡片标注未消耗）／ 用户分级（每个食材选必须或尽量）。
- **决定**：硬要求。今晚就是要消耗掉这些食材；无方案可消耗时明确告知，让用户删除或改天。
- **影响**：推翻旧设计"标记不过滤"的定义；推荐引擎的必消匹配从加分项变为过滤条件；菜库规模成为体验瓶颈（引出 PD-002）。

### PD-002 菜库 = 先跑通再扩
- **问题**：既然必消食材是硬要求，第一阶段菜库多大才够开始真实使用？
- **候选**：先跑通再扩（现有 3–4 套先验证功能）／ 补到 10–12 套再用（AI 起草、用户确认）／ 用户自己报菜名。
- **决定**：先跑通再扩。用现有菜库把流程真正用起来验证功能，菜库扩充放在流程验证之后。
- **影响**：初期会出现"没菜能消耗你输入的食材"的空手场景，属预期行为，UI 须把话说清；菜库扩充排在 TP-06。

### PD-003 换菜 = 给候选挑 + 原因可选
- **问题**："更换一道菜"时是什么体验？
- **候选**：一键自动换 ／ 候选挑选+原因可选 ／ 候选挑选+原因必填（旧设计）。
- **决定**：给候选挑。弹出同类型几道菜（带耗时/口味）供挑选；换菜原因改为可不填。
- **影响**：推翻旧设计"必填原因"；换菜必须真实替换（不再是假动作）；学习素材有损但不阻塞（学习闭环已推迟）。

### PD-004 购物清单 = 必消食材标"已有"不删
- **问题**：必消食材（家里已有的）在购物清单里怎么处理？
- **候选**：标"已有"不删 ／ 直接剔除 ／ 清单分两栏。
- **决定**：标出"已有"，不删除。核对时能发现存量不够，不会漏买。
- **影响**：清单模型需要"已有"标记；买菜前需扫一眼标注。

### PD-005 分量 = 按今晚人数自动缩放 + 取整
- **问题**：吃饭人数与菜谱分量（固定 4 人份）不一致时怎么办？
- **候选**：自动缩放+取整 ／ 不缩放照菜谱原样 ／ 只在减人时缩放。
- **决定**：按今晚人数自动换算，并凑成好买的整数（如 1.5 个鸡蛋 → 2 个）。
- **影响**：清单生成需引入人数缩放与取整规则；偶尔少量剩余属预期。

### PD-006 反馈 = 三问极简
- **问题**：每天晚饭后反馈填到什么程度？
- **候选**：三问极简 ／ 两问极简 ／ 旧设计五项完整。
- **决定**：三问：做了没？→ 好吃/一般/翻车？→ 下次还做吗？耗时改为选填。
- **影响**：旧反馈表单（实际耗时/失败原因等）简化；为未来学习保留关键信号；每日负担最小化。

### PD-007 使用场景 = 直接部署公网
- **问题**：第一阶段在哪里真实使用？
- **候选**：先家里局域网 ／ 直接上公网 ／ 修完再决定。
- **决定**：直接上公网。租云服务器（月费几十元），随时随地手机用。
- **影响**：部署从"以后再做"升级进本轮；产品负责人需准备云服务器与域名（国内需备案）；公网安全基线（移除前端令牌硬编码、禁 Mock 兜底）成为必做项。

- **决定**：确认，以此为准。后续修复与验收均以 PRODUCT-CONFIRMATION.md 为基准。
- **影响**：需求唯一事实源切换到 PRODUCT-CONFIRMATION.md；历史 PRD/实施方案降为对照资料。

### PD-009 菜品做法页 = 极简做法页移入本轮
- **问题**：选定一道菜后能不能看到详细做法？原确认书把「做法页完善」整体放在"以后再做"，方向稿评审时产品负责人指出这是缺口。
- **候选**：极简做法页进本轮（用料 + 分步文字，数据菜库已有）／ 维持原计划本轮不做 ／ 完整图文做法页进本轮。
- **决定**：加。本轮先做极简做法页——点今晚菜单里任意一道菜，可看用料（按人数缩放）与分步做法；图文/视频等增强仍留"以后再做"。
- **影响**：确认书 §四新增必备项、§六"以后再做"改为"做法页完善（图文/视频等增强）"；三套 UI 方向稿各补「菜品做法页」屏；开发时做法页直接使用菜库已有的分步做法字段，成本可控。

### PD-014 组合必消凑不进一桌时给出提示
- **问题**：必消多个食材（如西红柿+西蓝花）时，每样单独都有菜能用上，但没有一桌菜能同时用上全部——接口返回候选为空且 unmetMustUse 为空（T-P01 试点卡外发现#5，2026-09-06 实测）。页面若只显示通用空手文案，用户不知道问题出在"组合"上；要不要专门提示？
- **候选**：① 加组合空手专用提示（屏⑥变体文案，纯前端判定）／② 维持通用空手文案／③ 改引擎保证组合必消必有候选（需补种子菜单或改可行性语义，涉及契约与引擎，改动大）。
- **决定**：①，2026-09-06 用户拍板「需要提示」。前端按「candidates 为空 且 unmetMustUse 为空/缺省 且本地必消非空」判定，显示屏⑥变体文案（食材名按实际必消动态顿号连接）+「返回修改必消食材」按钮；不改契约、不改引擎 API；本地必消为空的退化场景保留通用文案兜底。
- **影响**：改动集中在 apps/h5 空态分支 + e-final.html 屏⑥变体 + design-spec.md 同步；C-7 单食材空手行为不变；契约无需新字段；UI 改动按流程先改确认书 B 节（2026-09-06 已增补屏⑥变体修订记录）再动代码。

### PD-017 空手文案区分时长原因（T-P05 验收反馈，2026-09-11）

- **候选**：① 屏⑥按原因分两型呈现（无菜型文案不变，时间型新文案含档位分钟数与出路暗示，混合两型分句说明）／ ② 维持现状单一文案 ／ ③ 另加快捷「换 60 分钟再试」按钮。
- **决定**：①，2026-09-11 用户批准 T-P10 技术方案（D-1~D-8 全按推荐：契约 record 侧车字段 `unmetReasons`、缺器具菜单不进宽集归无菜型、key 用用户原文、混合分句、不加快捷按钮、分钟数取用户当次所选档位、契约 v0.8 记 api.ts 头部）。组合凑不进一桌仍走 C-7a，不与两型混淆。
- **影响**：引擎 feasibility 增原因归类（空手判定行为零变化）；契约 v0.8 optional `unmetReasons`；planService/routes 透传；h5 屏⑥原因细分渲染；确认书 C-7 已按流程先行修订（2026-09-11）；屏⑥ UI 基准（e-final.html 时间型/混合型两帧 + design-spec.md）随实施同步。

### PD-018 推荐套餐按 MealRole 槽位动态组合（菜谱池类别化，2026-09-17）

### PD-020 一日三餐规划：解除「只管晚餐」，升级为次日三餐联合规划（T-Q05 扩展，2026-10-08）
- **问题**：产品负责人的真实痛点不是「今晚吃什么」，而是「帮家庭主理人解决一家人一天的餐饮搭配选择困难」——要按家人喜好/习惯/忌口/营养/多样性推荐搭配，且正常人习惯是一次性决定第二天的早中晚三餐、一次性买齐食材。确认书 A 部分「本版明确不做每日三餐（只管晚餐）」成为天花板。
- **候选**：① 解除「只管晚餐」限制，一次性升级为三餐联合规划（引擎/契约/DB/UI 四层重构）／ ② 渐进版先「晚餐→次日早餐」两餐跑通再扩三餐 ／ ③ 维持只管晚餐，只做 UI 换皮。
- **决定**：①，2026-10-08 用户逐项拍板（5/5）：按「一日三餐规划」推进；主控补充的 6 个方面全部采纳；儿童餐影响菜品选择（少辣/少刺/软烂）；「当天已吃的菜避开」窗口可调；推进节奏选一次性大改（A 方案）。
- **6 个采纳的补充方面**：① 想吃/必消/忌口冲突时如实说明不硬凑（沿用空手两型口径）；② 餐次可选（早/中/晚任选，不强制定全天，清单只含所选餐次）；③ 临时忌口（当日生效，如生病不吃牛肉）与长期硬禁忌分层；④ 当天视图按当前时间把「下一餐」置顶；⑤ 评价可选、按餐独立、漏评不追不催；⑥ 冷启动引擎无历史也能出餐，首次使用先引导填长期设置。
- **主流程（双周期）**：第 N 天晚上→首页（上：今天已定三餐供查看做法；下：「定明天的餐」）→设置（成人/儿童人数、必消、临时忌口、想吃的菜选填、餐次勾选）→推荐菜谱（引擎生成次日早/中/晚三餐）→逐餐审（换一道/换一餐/全部换一批）→确认→明日采购清单（三餐合并去重、成人+儿童换算、必消标已有、备菜建议分「今晚预处理/明早先做」）；第 N+1 天→首页看当天三餐→点菜看做法→做完按餐「记一笔」（评价可选）→评价进推荐依据；当晚回首页定后天的餐（今天已吃的进避开池）。
- **引擎逻辑**：长期（偏好菜系/硬禁忌/厨具/历史好评加权）+当日情境（成人/儿童人数、必消、临时忌口、想吃的菜）+避开重复（可调窗口，默认 7 天，沿用 A3 菜品级聚合）+营养搭配（三餐结构、主蛋白不重复、儿童餐少辣少刺软烂）+多样性（菜系/烹饪方式/主食材三餐不撞）。
- **影响**：确认书 A（§一产品一句话、§二核心问题、§三主流程、§四必备、§五本版不做、§六以后再做、§七成功标准）与 C（C-1~C-3a/C-4~C-6/C-7/反馈/历史 围绕「三餐」重写）全部修订（草案见 docs/design/v2/PD-020-confirmation-patch.md，待确认）；引擎从「单餐组合」→「三餐联合规划」（餐型维度+三餐去重/营养/多样性约束，L2）；契约 Plan 从「一套菜单」→「三餐×菜单」结构、Event 反馈按餐关联（L2）；DB schema Plan/Candidate 扩餐次字段、Feedback 按餐关联（L2 迁移）；UI 首页双周期视图+三餐菜单+按餐反馈（随 PD-019 新基准一并重做）；list-merger 三餐合并+成人/儿童换算。本决定与 PD-019 同属 T-Q05，实施拆卡执行。
