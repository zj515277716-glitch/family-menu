## 1. 目标（用户能完成的一件事）

必消空手时，屏⑥文案说清「为什么空手」：库里根本没有能用到该食材的菜（无菜型），还是有菜但今晚时长档排不下（时间型，正文给「换长时长再试」的出路暗示）；组合凑不进一桌仍走既有 C-7a 通道，不与两型混淆。

不做的：不引入第三型原因（如「器具缺失型」）、不加快捷换档按钮、不改 C-7/C-7a 既有文案措辞、不做 Plan 快照回填、不改推荐引擎的过滤语义与顺序（只增「原因归类」输出，空手判定行为零变化）。

### 现状勘误（与任务卡描述的差异，不影响方案成立）

1. **任务卡 AC1「苦瓜=无菜型对照」口径澄清**：苦瓜不是「库内食材但无菜消耗」，而是库外词（Ingredient 表查无，matcher 0 命中透传，F7）。在引擎层两者同为 NO_DISH 型、文案语义兼容（「暂时没有用上它的菜」对两者均如实），苦瓜可继续充当端到端层无菜型对照；纯「库内无菜消耗」场景由引擎单测 fixture（ing-tomato，F8）覆盖。
2. **planService 行号微差**：任务卡写「L500-520 全换分支」，实际全换分支的 recommend 调用在 [planService.ts L486-504](../../apps/api/src/services/planService.ts#L486-L504)、fallback 补足在 L518 起。行号差异不改变结论：全换分支响应是 Plan 而非空手，本方案不涉及该分支读取原因字段。
3. 其余卡内描述（feasibility L37-106、resolveMustUseIds L155-190、空手返回 L400-415、h5 L200-230 / L100-160、types L90-105）逐处核对与代码一致。

## 3. 方案设计

### 3.1 原因分类口径（引擎层纯函数，最小改动）

**核心：一轮循环双收集 + unsatisfiable 二次归类。不新增遍历、不改变任何过滤判定与 trace 顺序。**

定义「宽集」= 通过**器具过滤**（且经上游安全过滤）、**不限时长**的菜单的食材并集。分类规则：

- unsatisfiable 的必消 id ∈ 宽集 → `TIME_BUDGET`（有菜能用到，但今晚时长档排不下）
- unsatisfiable 的必消 id ∉ 宽集 → `NO_DISH`（放宽时长也没有菜能消耗它）

实现示意（feasibility.ts 改造后，trace 输出与现状逐元素一致）：

```ts
// 第一轮循环（改造后）
for (const menu of library) {
  const missing = collectMissingEquipment(menu, availableEquipment); // 提前计算，仅计算、不提前 push
  if (menu.totalActiveMinutes > context.timeBudgetMin) {
    filtered.push({ menuId: menu.id, stage: 'feasibility', rule: `总工时…超出预算…` }); // 顺序不变
    if (missing.size === 0) addIngredientIds(menu, wideIngredientIds);                  // 宽集收集（新增）
    continue;
  }
  if (missing.size > 0) {
    filtered.push({ menuId: menu.id, stage: 'feasibility', rule: `缺少器具：…` });       // 顺序不变
    continue;
  }
  reachable.push(menu);
  addIngredientIds(menu, wideIngredientIds); // reachable ⊆ 宽集
}
// unsatisfiable 判定（语义不变）+ 原因归类（新增）
for (const mustUseId of context.mustUseIngredients) {
  if (reachableIngredientIds.has(mustUseId)) continue;
  unsatisfiable.push(mustUseId);
  unsatisfiableReasons[mustUseId] =
    wideIngredientIds.has(mustUseId) ? 'TIME_BUDGET' : 'NO_DISH';
}
```

**口径论证**：

1. **器具过滤保留在宽集中（推荐口径，待裁决 D-2）**：若把缺器具菜单也计入宽集，一个只在缺器具菜单中出现的食材会被归为时间型，文案提示「换 60 分钟再试」是**假出路**（换任何档位都做不了）——出路暗示的真实性是本需求的底线。归无菜型的字面略有近似（库里有菜但家里做不了），但行为指引正确。若追求绝对精确需引入第三型 `EQUIPMENT`，扩契约枚举+文案+测试面，收益低，本期不做（记升级路径）。
2. **trace 顺序兼容**：器具检查提前计算但 push 条件与顺序不变（时长 trace 仍先于器具 trace、菜单仍按库序），score.spec.ts 既有顺序断言（如 L476 `filtered.map(f=>f.menuId)).toEqual(['menu-lawei','menu-plain-rice'])`）不破。
3. **组合语义与 C-7a 边界**：unsatisfiable 只对「连单菜单覆盖都为 0」的食材产出；组合凑不进（每样各有覆盖但无一桌同时覆盖全部）时 `unsatisfiable=[]`、原因字段缺省 → h5 判定优先级保证 C-7a 分支先于原因细分（见 3.5），天然不混淆。
4. **安全过滤天然前置**（F3）：宽集继承 safetyFilter 输出，含禁忌食材的菜单不会进入宽集，不会出现「含过敏原的菜被说成能用到但排不下」。
5. **性能**：宽集收集嵌入既有循环，零额外遍历；当前库规模 13 套菜单 × ~4 菜 × ~5 食材，增量是数百次 Set 操作，纳秒级。纯函数零 IO 零 LLM（DEC-006）。
6. **空手判定行为零变化**：`unsatisfiable: string[]` 的值、顺序、形状均不变，本方案只在其旁新增原因归类输出。

### 3.3 契约扩展（v0.8，须用户批准后实施）

**契约 diff**（[packages/shared/src/schemas/api.ts](../../packages/shared/src/schemas/api.ts#L189-L192)）：

```ts
export const RecommendResponseSchema = z.object({
  candidates: z.array(CandidateSchema),
  unmetMustUse: z.array(z.string()).optional(), // v0.3，语义不变
  /**
   * v0.8（T-P10/PD-017）：空手原因分类。
   * key = 用户原文（与 unmetMustUse 元素一一对应）；value = TIME_BUDGET（有菜但时长档排不下）
   * 或 NO_DISH（没有菜能消耗）。仅在空手且 unmetMustUse 非空时由服务端携带；正常推荐与
   * 组合凑不进（C-7a）时缺省。向后兼容：optional 增量（先例同 v0.3 unmetMustUse）。
   */
  unmetReasons: z.record(z.string(), z.enum(['TIME_BUDGET', 'NO_DISH'])).optional(),
});
```

**形态评估（待裁决 D-1，推荐 record 侧车字段）**：

| 维度 | 方案 R：`unmetReasons` record（推荐） | 方案 S：结构化数组 `unmet: Array<{raw, reason}>` |
|---|---|---|
| 既有字段 | unmetMustUse 原样保留，零回归 | 与 unmetMustUse 信息重复，两处数据源易漂移 |
| 前端消费 | `unmetReasons?.[raw]` 按 emptyReason 原文直查，零翻译 | 需遍历建索引，多一步映射 |
| 兼容性 | optional 纯增量 | 同为增量，但渲染主数据源要迁移到新结构，改动面大 |
| 极端场景 | mustUse 数组含重复原文时 record 键折叠（unmetMustUse 数组仍保留重复；仅 API 直调可触发，UI 防重复输入） | 可表达重复 |

**key 口径（待裁决 D-3，推荐用户原文）**：unmetMustUse 已是原文数组（idToRaw 回译），key 用原文则前端 `emptyReason`（原文数组）可直接索引；用 ingredientId 对前端无意义且需反向查询。API 层回译链路已存在（planService L410-412 同一 map）。

**账本落点（待裁决 D-7）**：v0.8 记 **api.ts 头部**（追加一行 v0.8 摘要）+ RecommendResponseSchema 注释——顺 CURRENT.md 挂账⑨「收敛回 api.ts 单一入口」方向；v0.7 在 dish.ts 头部的存量**本卡不做收敛**（收敛是卡外工作，仅在 v0.8 注释中注明「历史版本 v0.2~v0.7 见 api.ts 头部与 dish.ts 头部」）。shared/src/types/index.ts 无需改动（`RecommendResponse` 经 `z.infer` 自动获得新字段，L118 既有导出）。

### 3.5 h5 渲染与文案草案（须用户批准后实施）

**类型**：[apps/h5/src/types/index.ts](../../apps/h5/src/types/index.ts#L102-L106) `RecommendResult` 增 `unmetReasons?: Record<string, 'TIME_BUDGET' | 'NO_DISH'>`。

**三态判定优先级**（tonight/index.tsx 屏⑥分支，改造最小化——只细分 `emptyReason.length > 0` 分支内部）：

1. `emptyReason.length === 0` → **现状分支原样**：必消非空 = C-7a（composeEmptyTitle）、必消空 = DEC-012 兜底。此路径不读 unmetReasons（此时字段必然缺省），C-7a 与两型天然隔离。
2. `emptyReason.length > 0` → 按原因细分（对 emptyReason 各原文查 `unmetReasons?.[raw]`）：
   - a. `unmetReasons` 缺省（防御分支：同仓同发不可达，仅 h5 先发/旧后端组合）→ 全部按**无菜型**渲染 = 现状文案，零回归兜底；
   - b. 全部 `NO_DISH` → **无菜型**（现状标题与正文原样不动）；
   - c. 全部 `TIME_BUDGET` → **时间型**（新文案）；
   - d. 混合（部分各型）→ **混合型**（标题沿用现状模板，正文分句说明，待裁决 D-4）。

**档位分钟数口径（待裁决 D-6）**：渲染 `tonightContext.timeBudgetMin`（用户当次所选档位，与本次推荐请求参数同源），不从响应取、不取 FamilyRule.timeBudgets[0]——用户看到的角度数永远是他刚选的档。

**按钮组**：三型全部维持现状按钮（「去掉『X』再试」handleRetryWithoutUnmet 逻辑不变、「返回修改必消食材」），出路暗示放正文；快捷「换 60 分钟再试」按钮**不做**（待裁决 D-5：档位序列 FamilyRule.timeBudgets 用户可配、「下一档」语义需定义，正文暗示已达目标，AC4 只要求文案）。
