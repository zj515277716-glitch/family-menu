## 一、目标与范围锁定（v0.1）

### 1.1 服务对象与成功标准

- **用户**：苏大侠家4口（1名主理人操作，其他人只看结果）
- **成功标准**（对应文件③9.6规模压力测试"1个家庭"行）：**连续4周，每周至少完成2次"计划→做出来"的晚餐**
- **核心承诺**：2分钟内定下今晚吃什么，并拿到采购清单和备菜顺序

### 1.2 v0.1 必须实现（P0，对应④5.2/文件③7.3）

| # | 功能 | 验收口径 |
|---|---|---|
| F1 | 家庭规则设置 | 人数/绝对禁忌/常用时长/器具/偏好菜系，首次设置≤90秒 |
| F2 | 今晚情境输入 | 人数、时间档（15/30/60分钟）、最多3个必须消耗食材 |
| F3 | 三套菜单候选 | 每套显示总耗时、难度、主食材、推荐理由；整套换/单菜换（记录原因） |
| F4 | 采购清单 | 按品类分组、同食材合并、单位归一、可勾选 |
| F5 | 备菜顺序 | 菜单级并行工序：先洗切什么、何时起锅 |
| F6 | 极简反馈 | 锁定/做了/没做/下次还做；其余从行为推断 |
| F7 | 历史与复做 | 成功菜单一键复用 |

### 1.3 v0.1 明确不做（YAGNI清单）

**产品层**（文件③5.3）：成员独立账号、每日三餐、投票、完整库存、拍照识别、儿童生长、社区、营养处方。
**技术层**：微服务、Redis、消息队列、K8s、SSR、监控平台、多环境（只有 local + prod）、微信登录（用访问口令代替）、**运行时LLM调用**（⑤2.2三重收益原则）。

## 二、技术栈定案

| 层 | 选型 | 理由 | 否决的备选及原因 |
|---|---|---|---|
| 运行时 | **Node.js 22 LTS** | 生态最全，各AI Agent训练语料最熟，出错率最低 | Bun/Deno：生态边角坑会消耗Agent调试轮次 |
| 语言 | **TypeScript（strict）** | 类型即契约——多Agent并行开发的基础设施 | JS：无契约，Agent间接口漂移无法及早暴露 |
| 包管理 | **pnpm workspace（monorepo）** | 共享类型包=前后端Agent的单一事实源 | 多仓库：契约同步成本高，不适合单人+多Agent |
| API框架 | **Fastify 5 + zod**（fastify-type-provider-zod） | 轻量、schema校验原生、可自动导出OpenAPI给前端Agent当Mock契约 | NestJS：样板重，自用版规模不值；Express：类型弱、生态老化 |
| ORM | **Prisma** | schema文件即数据库文档，migration内建，Agent生成准确率业界最高 | Drizzle：更轻但Agent熟练度略低；TypeORM：维护状态差 |
| 数据库 | **PostgreSQL 18.3（阿里云RDS，已有）** | ⑤2.1定案：关系模型匹配"食材—菜品—替换关系图"核心资产 | —（本地开发用Docker起同版本PG，RDS只做线上，见9.4） |
| 前端 | **Taro 4 + React 18 + NutUI** | **一码两端**：现在编译H5（备案过渡期家人微信内打开），阶段2切weapp编译目标零重写 | 原生小程序：H5期无法用；uni-app(Vue)：React生态Agent更熟 |
| 状态管理 | **Zustand** | 自用版状态简单，够用且Agent不易写错 | Redux：仪式感过重 |
| 管理后台 | **Vite + React + AntD 5**（P1） | CRUD后台是Agent最擅长的产出物，半天可成 | 先用Prisma Studio本地看数据顶一周 |
| 测试 | **Vitest** | 引擎/合并器是纯函数，单测性价比极高 | Jest：慢，配置多 |
| 部署 | **Docker Compose + Caddy**（ECS，已有） | 可复现、Agent写得对；Caddy备案通过后自动HTTPS | 裸装PM2：环境漂移，换机重来 |
| 内容管线 | **火山方舟 OpenAI兼容SDK（豆包，已有订阅）** | ⑤2.3定案：只在**生产时**起草，运行时零调用 | Claude中转API：⑤3.8红线——不碰生产链路 |

**代码仓库位置建议**：`D:\codex\family-menu`（独立英文路径，避开中文路径在部分工具链的边缘问题；文档仓与代码仓分离）。

## 三、系统架构与数据模型

### 3.1 运行架构

```text

        │                             │                              │ 调用豆包API起草
        ▼                             ▼                              ▼ 产出JSON→人工试做→导入
   Caddy(443, 备案后) / 直连IP:3000(过渡期)
        │
   Fastify API ──── packages/engine（推荐，纯函数）
        │      └─── packages/list-merger（清单合并，纯函数）
        ▼
```

### 3.2 Prisma Schema（数据模型骨架，WP-02的起点）

```prisma
// apps/api/prisma/schema.prisma
generator client { provider = "prisma-client-js" }
datasource db { provider = "postgresql"; url = env("DATABASE_URL") }

// ───── 家庭与规则 ─────
model Family {
  id         String          @id @default(cuid())
  name       String
  rule       FamilyRule?
  exclusions ExclusionRule[]
  plans      Plan[]
  events     Event[]
  createdAt  DateTime        @default(now())
}

model FamilyRule {
  id            String   @id @default(cuid())
  familyId      String   @unique
  family        Family   @relation(fields: [familyId], references: [id])
  defaultPeople Int      @default(4)
  timeBudgets   Int[]    // 常用时长档，如 [30, 60]
  equipment     String[] // wok/rice_cooker/steamer/air_fryer
  cuisines      String[] // 如 湘菜/家常
  updatedAt     DateTime @updatedAt
}

// 硬软分离是文件③7.4的核心修正：HARD=过敏/绝对禁忌(过滤)，SOFT=不喜欢(降权)
model ExclusionRule {
  id        String         @id @default(cuid())
  familyId  String
  family    Family         @relation(fields: [familyId], references: [id])
  scope     ExclusionScope // INGREDIENT | DISH | TAG
  targetId  String?        // ingredientId 或 dishId
  targetTag String?        // scope=TAG 时用，如 "内脏"
  severity  Severity       // HARD | SOFT
  note      String?        // "爸爸不吃腊肉"
}
enum Severity       { HARD SOFT }
enum ExclusionScope { INGREDIENT DISH TAG }

// ───── 内容资产（核心壁垒，④推翻清单#9）─────
model Ingredient {
  id          String           @id @default(cuid())
  name        String           @unique
  aliases     String[]         // 别名归一：西红柿=番茄
  category    String           // 蔬菜/肉类/水产/蛋奶/调料/主食
  defaultUnit String           // g/个/块...
  dishes      DishIngredient[]
  subsFrom    Substitution[]   @relation("from")
  subsTo      Substitution[]   @relation("to")
}

model Substitution {
  id           String     @id @default(cuid())
  ingredientId String
  substituteId String
  ratio        Float      @default(1)
  note         String?
  from         Ingredient @relation("from", fields: [ingredientId], references: [id])
  to           Ingredient @relation("to", fields: [substituteId], references: [id])
}

model Dish {
  id            String           @id @default(cuid())
  name          String
  mealRole      MealRole         // MAIN | SIDE | SOUP | STAPLE
  cuisine       String?
  flavorTags    String[]         // 清淡/微辣/酸甜...
  spicyLevel    Int              @default(0)
  splitFlavor   Boolean          @default(false) // 可拆分调味（儿童清淡/成人辣）
  activeMinutes Int              // 动手时间
  totalMinutes  Int              // 含炖煮等待
  equipment     String[]
  steps         Json             // [{order, text, parallel?}]
  status        ContentStatus    @default(DRAFT)   // DRAFT→TESTED→PUBLISHED
  origin        ContentOrigin    @default(LLM_DRAFT)
  licenseNote   String?          // 内容授权台账字段（⑤2.1）
  ingredients   DishIngredient[]
  menus         MenuDish[]
  cookLogs      CookLog[]
}
enum MealRole      { MAIN SIDE SOUP STAPLE }
enum ContentStatus { DRAFT TESTED PUBLISHED }  // 只有PUBLISHED进入推荐池
enum ContentOrigin { LLM_DRAFT MANUAL }

model DishIngredient {
  id           String     @id @default(cuid())
  dishId       String
  ingredientId String
  qty          Float
  unit         String
  optional     Boolean    @default(false)
  dish         Dish       @relation(fields: [dishId], references: [id])
  ingredient   Ingredient @relation(fields: [ingredientId], references: [id])
}

// "一套饭"是一等对象（文件③7.2），不是菜品的松散集合
model Menu {
  id                 String        @id @default(cuid())
  name               String        // "番茄牛腩套餐"
  scene              MenuScene     // WEEKDAY_FAST | WEEKEND | CLEARANCE | BUDGET
  serves             Int           @default(4)
  totalActiveMinutes Int           // 并行工序后的真实总工时（≠单菜相加）
  prepSequence       Json          // [{minute, action}] 备菜顺序
  status             ContentStatus @default(DRAFT)
  dishes             MenuDish[]
  cookLogs           CookLog[]
}
enum MenuScene { WEEKDAY_FAST WEEKEND CLEARANCE BUDGET }

model MenuDish {
  menuId String
  dishId String
  sort   Int
  menu   Menu   @relation(fields: [menuId], references: [id])
  dish   Dish   @relation(fields: [dishId], references: [id])
  @@id([menuId, dishId])
}

// 试做记录：菜单从DRAFT升级TESTED/PUBLISHED的唯一通道（⑤2.3内容管线）
model CookLog {
  id            String   @id @default(cuid())
  menuId        String?
  dishId        String?
  cookedAt      DateTime @default(now())
  actualMinutes Int?
  result        String   // success | partial | fail
  failPoints    String?
  willRepeat    Boolean?
  menu          Menu?    @relation(fields: [menuId], references: [id])
  dish          Dish?    @relation(fields: [dishId], references: [id])
}

// ───── 运行数据 ─────
model Plan {
  id           String     @id @default(cuid())
  familyId     String
  family       Family     @relation(fields: [familyId], references: [id])
  planDate     DateTime
  context      Json       // {people, timeBudgetMin, mustUse: string[]}
  candidates   Json       // 3套候选快照：[{menuId, score, reasons, breakdown}]
  lockedMenuId String?
  shoppingList Json?      // 合并后清单快照 + 勾选状态
  status       PlanStatus @default(PROPOSED)
  events       Event[]
  createdAt    DateTime   @default(now())
}
enum PlanStatus { PROPOSED LOCKED COOKED SKIPPED }

// 行为事件=隐式反馈源（④推翻清单#4），也是未来商业验证的埋点
model Event {
  id        String    @id @default(cuid())
  familyId  String
  planId    String?
  type      EventType
  payload   Json?     // swap时记 {reason: "太麻烦"}
  createdAt DateTime  @default(now())
  family    Family    @relation(fields: [familyId], references: [id])
  plan      Plan?     @relation(fields: [planId], references: [id])
}
enum EventType { GENERATE VIEW LOCK SWAP_MENU SWAP_DISH COOKED NOT_COOKED REPEAT }
```

**设计要点回溯：** 硬软禁忌分离（文件③7.4）｜Menu为一等对象（文件③7.2）｜status三态让"未试做的LLM草稿"永远进不了推荐池（安全底线）｜Event表即埋点，礼宾期漏斗指标直接可算｜familyId全链路贯穿，阶段2多家庭零改造。

## 四、推荐引擎设计（packages/engine，纯函数）

### 4.1 三层管道（文件③7.4）+ 输出可解释

```text
输入: rules + exclusions + context + library(仅PUBLISHED) + history(近30天events)
  │
  ├─ 第一层 safetyFilter    HARD禁忌过滤；成分未确认的菜单直接滤除 → 产出 FilterTrace
  ├─ 第二层 feasibilityFilter 时长/器具硬过滤；mustUse无法消耗→标记而非过滤
  ├─ 第三层 score           菜单分 = 0.35×历史接受度 + 0.20×时长难度匹配
  │                              + 0.15×现有食材复用(mustUse命中)
  │                              + 0.10×偏好覆盖(SOFT禁忌降权在此)
  │                              + 0.10×近期多样性(7天内做过降权)
  │                              + 0.10×膳食类别多样性
  └─ 第四层 diversify       取Top-N后错开主蛋白/风格，输出3套 + 每套reasons[]
```

### 4.2 核心接口签名（packages/engine/src/types.ts，契约的一部分）

```ts
export interface TonightContext {
  people: number
  timeBudgetMin: 15 | 30 | 60
  mustUseIngredients: string[]   // 最多3个，ingredientId
}

export interface RecommendInput {
  rules: FamilyRuleView
  exclusions: ExclusionView[]
  context: TonightContext
  library: MenuView[]            // 仅 status=PUBLISHED
  history: EventView[]           // 近30天
}

export interface ScoredMenu {
  menuId: string
  score: number
  reasons: string[]              // ["30分钟内可完成", "消耗你标记的番茄", "本周没吃过鱼"]
  breakdown: Record<ScoreDim, number>
}

export interface FilterTrace {   // 可解释性：为什么被滤（文件③9.4推荐解释要求）
  menuId: string
  stage: 'safety' | 'feasibility'
  rule: string                   // "含腊肉，命中HARD禁忌#x"
}

export function recommend(input: RecommendInput): {
  candidates: ScoredMenu[]       // 恰好3套（不足3套时如实返回并说明）
  filtered: FilterTrace[]
}
```

**铁律：** 引擎零IO、零LLM、零数据库依赖——输入输出全是内存对象。这让它可以被100%单测覆盖，且API层/未来小程序云函数均可复用。安全层永远先于评分，不可被任何权重覆盖（文件③7.4）。

### 4.3 禁忌测试集（WP-10，阻断率100%是发布门槛）

- fixtures生成：每条HARD规则 × 库内每套含该成分的菜单 = 一条必须被过滤的用例；
- 变形用例：别名（番茄/西红柿）、隐含成分（腊味合蒸含腊肉）、可选食材含禁忌；
- 断言：`filtered`包含之且`candidates`不含之；CI每次跑，失败即阻塞合并。

### 4.4 采购清单合并器（packages/list-merger，纯函数）

```ts
mergeShoppingList(menu: MenuView): ShoppingList
// 职责：同食材合并(经aliases归一) → 单位换算(unit表) → 按category分组 → 去除家庭常备调料(可配置)
```
单位合并是文件③9.2点名的故障点，独立成包、独立测试（错误率<1%门槛）。

### 5.2 UI素材管线（三层素材策略）

> 机制：UI/UX设计Agent从总方案推导出**风格提示词基座**与**素材清单spec**，你把提示词批量投喂给生图工具（ChatGPT已有Plus；国产替代：即梦/豆包生图）**一次成套生成**——风格统一由"基座复用"保证，精准控制由"清单spec"保证。

**三层策略（哪类素材用哪种来源）：**

| 层 | 素材 | 来源 | 理由 |
|---|---|---|---|
| 功能图标 | tabBar/操作/分类icon | **图标库**（NutUI内置+iconfont补充） | AI生图产SVG弱、小尺寸批量一致性差；图标库矢量、免费、风格天然统一 |
| 装饰插画 | logo、引导页、空状态×3、锁定成功反馈、周报头图、菜品**占位**图 | **AI生图**（约10–12张） | 量少但设计成本高，AI最划算；无真实性问题 |
| 菜品照片 | 每道菜/每套菜单主图 | **试做实拍**（内容轨试做时顺手拍摄） | ①真实=信任：AI菜品图"图不符实"直接损害锁定率（文件③9.2同族风险）；②法律零风险；③与"每套菜单必须试做"管线零成本融合 |

**风格提示词基座**（写入`docs/design/assets-spec.md`，所有插画提示词=基座+素材专属描述）：

```text
基座示例：扁平插画风格，暖橙+奶油白主色调，圆角造型，家庭厨房主题，
柔和光影，画面简洁无文字，统一描边粗细，平视视角
＋素材专属：空状态-无计划页｜一只空盘子和一双筷子，旁边一个问号气泡（480×360）
```

**assets-spec.md 必含字段**：素材名／用途页面／尺寸与格式（@2x PNG/WebP）／命名（`asset-{page}-{name}@2x.png`）／完整提示词／生成状态。

**一致性纪律**：①同一会话连续生成全套，首张定稿后作为参考图续生；②一次成套、入库即锁定，不单张补生（**跨批次风格漂移是主要失败模式**）；③视觉定稿=人工决策点（6.4）。

**边界**：AI素材仅用于装饰性UI，不生成"以假乱真"的菜品实拍感图片（避免误导）；AI图版权在国内司法实践有争议，装饰用途风险低；占位图与实拍图不混用场景。

### 6.2 团队拓扑：单底座分Agent（混合制衡型，DEC-009）

### 6.5 对齐机制：四件套（直接沿用买菜平台已验证模式）

买菜平台项目（STEP-00~09+FEATURE-01/02全程跑通）验证了一套"仓库文件即唯一事实源"的对齐机制，其无上下文恢复演练证明：**全新会话的Agent仅凭仓库文件即可准确恢复当前任务、边界与门禁**。本项目全盘移植：

| 文件 | 职责 | 维护者 |
|---|---|---|
| `AGENTS.md` | 角色、铁律、Ownership、常用命令（附录A） | 主Agent |
| `STATUS.md` | **唯一活动任务卡**+当前状态快照（main HEAD、回滚tag、阻塞项、下一决策点）+总任务拆解表 | 仅主Agent |
| `DECISIONS.md` | 跨步骤有效的决策DEC-xxx；普通实现细节不入内 | 仅主Agent |
| `开发日志.md` | append-only审计：每STEP五段记录（START/DEV/TEST/REVIEW/COMPLETE），含可复制命令+退出码+数字证据 | 各角色追加 |

**四条核心协议**（登记为DEC-003~005，全文见附录D）：

1. **无上下文恢复协议**：每步开始前完整读取实施方案+四件套；仓库文件与测试结果**优先于聊天上下文**；每步结束必须追加开发日志，未记录不得开始下一步。（简化：以git commit hash替代买菜平台的逐文件SHA256——当时其`.git`为空故需哈希，本项目自STEP-00即有git保证完整性）
2. **WIP=1**：代码任务串行，`STATUS.md`任何时刻只有一个活动任务卡；内容/素材轨道除外（6.2）。
3. **用户审核门禁**：每STEP完成开发→独立测试→交叉审查→主复验后，状态停在"**待用户审核**"；你批准前不合并、不启动下一STEP；内部审查不得当作用户审核。
4. **回滚tag+基线提交**：每STEP开工前打`rollback-before-step-xx` tag并在任务卡记录基线commit；合并采用非快进方式保留任务边界。

框架2.4"云引用禁本地路径"在此等价实现：产物=仓库相对路径@commit；任务评论=日志五段记录+任务卡完成/审查报告；代码=分支名+commit。上下文最小化原则不变：派发只给本卡+契约+上游产物路径。

### 6.6 裁剪与决策定案（可逆，阶段2可升格回严格版）

框架自身支持裁剪（bug修复走"环节4–6裁剪版流水线"、扩展点"只声明不预实现"）。四项定案：

1. **分支策略裁剪**：v0.1用 `main + task/step-xx-*` 分支（沿买菜平台命名）、非快进合入main并打回滚tag，跳过develop/release。理由：只有local/prod两套环境，develop无集成环境可绑定。阶段2多端多人时恢复完整Git Flow精简版。
2. **环境分层裁剪**：四套→两套（local/production）。integration/staging在单体+单家庭下无独立收益；阶段1礼宾开始前补staging（RDS影子库）。配置结构两套保持一致，仅环境变量不同（框架"配置模板+环境变量注入"原则保留）。
3. **编排载体定案**：采用**四件套文件驱动**（买菜平台模式，已实战验证）。Hermes agent若具备任务系统能力可作为执行器接入，但机制不变——四件套仍是唯一事实源。
4. **并发模型定案**：代码WIP=1串行（买菜平台DEC-003原样沿用）+内容/素材非代码轨并行（本项目扩展）。放弃原"3泳道代码并行"：用户审核门禁下并行分支只会堆积待审，且串行让你每晚只审一件事、合并零冲突。**代价：总工期从14天修正为约3周（8.1）**。
5. **运行底座定案**：全部角色在**Trae**内以自定义智能体承担（2026-08-06三条件实测通过后定案，见6.2/DEC-009）；放弃原"角色分散到多工具"——跨工具无消息总线，人工中转每STEP约4–6次且必丢上下文。跨模型制衡压缩为M1–M4四次gate审查（由**Claude Code**执行），不进STEP内流程。
